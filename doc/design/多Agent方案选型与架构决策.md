# 多Agent方案选型与架构决策

> **文档用途：** 记录 TicketAgent 项目多 Agent 系统的架构选型过程，说明主流方案的特点与差异，以及我们选择当前架构的理由。
> 
> **创建日期：** 2026-07-25  
> **项目背景：** 2周实习生项目，信用卡工单处理多Agent系统

---

## 一、方案概览

### 1.1 业界主流多Agent编排方案

| 方案类型 | 代表技术/框架 | 核心特点 | 适用场景 |
|---------|--------------|---------|---------|
| **固定流水线** | 自研 orchestrator | 线性/固定分支，显式状态传递 | 业务流程确定、步骤固定的场景 |
| **有向图编排** | LangGraph, AutoGen | 支持循环、条件分支、状态回溯 | 需要动态决策、人在环、复杂状态管理 |
| **跨Agent通信协议** | A2A (Agent-to-Agent Protocol) | 标准化跨组织/跨厂商Agent互操作 | 分布式、跨组织的Agent协作 |
| **Agent生成UI** | A2UI (Agent-to-UI) | Agent动态生成/驱动前端界面 | 需要根据Agent输出动态构建界面 |
| **标准作业流程** | SOP配置化 (MetaGPT思路) | 业务流程显式编码为可配置规则 | 业务规则明确、需要合规审计 |
| **UI自动化兜底** | PageAgent (ReAct + 浏览器操作) | 无侵入式操作现有系统页面 | 无API或不可改造的外部/遗留系统 |

## 二、TicketAgent 当前架构

### 2.1 架构选择

**核心方案：** **固定流水线 + 确定性规则快车道 + LLM慢车道混合**

```
Classifier → Intake → Escalation → Resolution → Notification
   (分类)    (抽字段)   (升级判断)    (选工具)      (生成回复)
```

每个Agent内部：
- **规则优先：** 对结构化、有明确特征的输入，用正则/字典映射快速处理
- **LLM兜底：** 规则miss时(如必填字段未抽全、语义模糊)才调用LLM

**配置驱动：** 业务场景参数(字段定义、工具映射、SLA、通知模板)统一存储在 `workflow_config.json`

### 2.2 技术特征

- **编排复杂度：** 低(5步固定线性流水线)
- **状态管理：** 简单(PipelineContext线性传递)
- **可观测性：** TraceCollector + SSE实时流式输出
- **成本控制：** 规则优先，LLM按需调用

## 三、方案对比与决策理由

### 3.1 为什么不选 LangGraph？

**LangGraph 适用场景：**
- 需要复杂条件分支(如"工具调用失败 → 换策略重试 → 仍失败转人工")
- 需要循环结构(如"反复调用工具直到收集齐信息")
- 需要状态回溯(如"Agent2发现Agent1的输出有问题，回退重来")
- 人在环路(如"Agent提出方案 → 等人确认 → 继续执行")

**我们的实际需求：**
- 工单处理是**固定5步线性流程**，没有复杂分支/循环
- 状态传递是单向的(Classifier → Intake → ... → Notification)
- 人工介入由 Escalation 的 `can_auto_proceed=False` 显式标记，不需要回退

**决策理由：**
1. **当前规模不需要：** 5步流水线用 LangGraph 是用火箭炮打蚊子，徒增复杂度
2. **重写成本高：** 需要把5个Agent改写成 StateGraph 节点，至少2-3天，风险高
3. **核心问题不在编排：** 我们的痛点是"LLM路径未接通"和"配置分散"，换LangGraph解决不了这两个问题

**何时该引入：**
- 如果未来需要"调用外部API失败自动重试3次，每次换不同参数"这类循环逻辑
- 如果需要"Agent自主决定下一步要跳回哪个节点"的动态流程
- 如果业务场景从7个扩展到30+个，开始出现大量场景特定的分支逻辑

**答辩话术：**
> "我评估过LangGraph，它解决复杂编排和状态回溯问题。我们当前是固定5步线性流程，状态传递单向，用LangGraph会引入不必要的复杂度。如果后续需要动态分支或人在环，可以平滑迁移。"

---

### 3.2 为什么不选 A2A (Agent-to-Agent Protocol)？

**A2A 适用场景：**
- **跨组织协作：** 银行A的Agent需要调用保险公司B的Agent
- **跨厂商互操作：** 不同AI平台(OpenAI/Claude/Gemini)的Agent互相发现和通信
- **分布式部署：** Agent分布在不同服务/网络边界，需要标准化通信协议

**我们的实际需求：**
- 5个Agent都在**同一个Python进程内**
- Agent间通信本质是**函数调用**(`orchestrator.classifier_agent.run(context)`)
- 没有跨组织/跨服务的需求

**决策理由：**
1. **协议开销无意义：** A2A是网络协议，用它在进程内通信是拿HTTP协议替代函数调用
2. **完全不匹配需求：** 我们没有"Agent发现""跨组织授权"这些分布式问题
3. **徒增复杂度：** 需要序列化/反序列化消息，增加延迟和故障点

**何时该引入：**
- 如果TicketAgent需要调用**其他公司/部门的独立Agent服务**(如调用风控部门的独立反欺诈Agent)
- 如果需要把5个Agent拆分成**独立部署的微服务**，跨网络通信

**答辩话术：**
> "A2A是为跨组织、跨厂商的分布式Agent设计的协议。我们的Agent在同一进程内协作，用函数调用即可，引入A2A是架构过度设计。"

---

### 3.3 为什么不选 A2UI (Agent-to-UI)？

**A2UI 适用场景：**
- Agent根据输出**动态生成前端界面**(如生成一个可视化报表、构建交互表单)
- 需要让Agent**自主决定展示什么UI组件**

**我们的实际需求：**
- 前端是**固定的工单/回单页面**，表单结构由业务定义，不需要动态生成
- Agent输出的是**结构化数据**(字段、工具调用结果、通知文本)，前端按固定模板渲染

**决策理由：**
1. **前端已定型：** 工单表单、回单界面都是固定结构，不需要Agent现场画界面
2. **无应用场景：** 我们的Agent是业务处理节点，不是UI生成器

**何时该引入：**
- 如果需要让Agent根据不同场景**动态生成不同的表单/报表**(如某些场景需要额外字段、某些场景需要可视化图表)

---

### 3.4 SOP (标准作业流程) —— 我们已经有了

**SOP 概念：**
把业务流程显式编码成Agent遵循的标准作业规则(MetaGPT等思路)。

**我们的实现：**
`workflow_config.json` **本质上就是SOP层**：
- `required_fields` —— 必须收集哪些信息
- `recommended_tool` —— 该调用哪个工具
- `notification_template` —— 标准回复话术
- `requires_human_confirmation` —— 哪些情况必须人工介入
- `slaDays` —— 处理时限

**当前问题：**
SOP配置分散在6个地方(config + FITS_SCENARIOS元组 + 正则 + Classifier prompt + 工具映射 + 字段schema)，需要收敛成**唯一真相源**。

**优化方向(P1优先级)：**
1. 删掉 `intake_agent.py` 的 `_FIELD_SCHEMAS`，改从config读
2. 删掉 `resolution_agent.py` 的 `_INTENT_TOOL_MAP`，改从config读
3. Classifier的系统prompt里的场景列表改成从config动态拼接
4. 做完后，新增场景 = 只改一条JSON

**答辩话术：**
> "我们已经实现了SOP配置化，把业务流程参数抽象到workflow_config.json。当前优化重点是收敛配置，让它成为唯一真相源，实现真正的'新增场景=改一条JSON'。"

### 3.5 PageAgent 的两个方向抉择

**背景：** PageAgent 当前定位是"无侵入式兜底方案"。

#### 方向对比

| 方向 | 做法 | 适用场景 | 问题 |
|------|------|---------|------|
| **方向1** | 多Agent处理后的信息穿给PageAgent，通过操作页面完成填单 | 回单后端**不能改/不让改** | 对自有系统这是倒退：POST一句话能干的事，变成脆弱的DOM操作 |
| **方向2** | 回单Agent直接POST请求完成填单，PageAgent只在需要操作**外部系统**(Agent未接入)时介入 | **外部/遗留系统无API** | ✅ 正确架构 |

#### 决策理由

**选择方向2的核心原则：**
> **能用API/POST就用API，UI自动化只做"没有API或没接入的系统"的兜底。**

**理由：**
1. **API直连的优势：** 快、可靠、可测试、不怕页面改版
2. **UI自动化的劣势：** 慢(需要渲染页面、等待加载)、脆(DOM一改就崩)、错误难处理(看不到具体报错)
3. **"无侵入"的真正价值：** 对那些**你没有API、改不动、或不想改的外部系统**(如遗留CRM、第三方平台)，PageAgent才是唯一出路

**架构定义：**
```
回单系统(自有) → Agent直接POST填单
外部系统(无API) → PageAgent操作页面
```

**方向1的唯一成立条件：**
如果回单后端**受管控、非你所有、不允许新增API**，那UI自动化才是必选项——这正是"无侵入"三个字的全部意义。但本项目回单系统是自己的，所以走方向2。

**答辩话术：**
> "PageAgent的价值在于'无侵入式操作外部系统'。对自有回单系统，我们用POST直连(快、可靠)；PageAgent只在需要操作第三方/遗留系统(如某些银行内部老系统无API)时才介入，这样最大化可靠性，最小化脆性。"

## 四、当前架构的核心优化(P0/P1)

### 4.1 P0：让LLM路径真正接通

**问题：**
- IntakeAgent的LLM路径是死代码(只要有字段就短路返回，`call_llm`永远不跑)
- Classifier/Resolution的LLM路径几乎不会触发

**优化：**
把"只要有字段就返回"改成"**必填字段没抽全时**才fallback到LLM"：
```python
# 改前(intake_agent.py:142)
if deterministic_fields:  # 总是True → 短路
    return {"fields": deterministic_fields}

# 改后
required = self.workflow_config.scenarios[scene_type].required_fields
missing = [f for f in required if not any(d["name"]==f and d["value"] not in MISSING_VALUES for d in deterministic_fields)]
if not missing:  # 必填字段都齐了
    return {"fields": deterministic_fields}
# 否则走LLM
```

**效果：**
- 规整工单(字段格式标准) → 规则快车道(省token、快)
- 刁钻工单(口语化、字段藏在正文里) → LLM慢车道(兜住)
- **可演示对比，证明混合架构的价值**

### 4.2 P1：配置收敛成唯一真相源

**问题：**
新增场景需要改6个地方，打脸"配置驱动"。

**优化：**
- 删除 `_FIELD_SCHEMAS`、`_INTENT_TOOL_MAP` 等硬编码字典
- 所有Agent从 `workflow_config.json` 动态读取
- Classifier的场景列表prompt从config拼接

**效果：**
新增场景 = 只改一条JSON，真正实现配置驱动(同时也是SOP配置化的完整实现)。

## 五、总结：架构选型的判断原则

| 原则 | 说明 | 体现 |
|------|------|------|
| **复杂度与需求匹配** | 用能解决问题的最简单方案，不过度设计 | 不引入LangGraph/A2A |
| **API优先于UI自动化** | 能直连就直连，UI自动化只做兜底 | PageAgent只管外部系统 |
| **配置驱动** | 业务规则显式化为可配置SOP | workflow_config.json |
| **规则与LLM分工** | 规则处理结构化输入(快、省)，LLM处理语义理解(兜底) | 混合架构 |
| **可演示的优化** | 1天时间优先做能现场演示效果的改动 | P0 > P1 > 讲故事 |

**答辩策略：**
- **不要堆技术名词，要讲架构判断。** 说清楚"我评估过X，判断当前不需要，理由是Y"
- **把当前架构的优点讲透。** 混合架构、配置驱动、SOP化已经是正确方向，做实它比换框架有价值
- **用对比演示说话。** 现场跑一个规则路径 vs LLM路径的对比案例，比口头讲有说服力

## 六、未来演进路径

### 6.1 短期(1-3个月)
- P1做完后，扩展到更多业务场景(当前7个 → 20+)
- 补齐 PageAgent 对外部系统的集成案例

### 6.2 中期(3-6个月)
- **如果出现复杂分支需求**(如工具调用失败自动重试、动态决定回退)，考虑引入 LangGraph
- **如果需要跨部门Agent协作**(如调用风控部门的独立服务)，考虑引入 A2A

### 6.3 长期(6个月+)
- 积累场景数据后，训练场景分类/字段抽取的微调模型，降低LLM成本
- 考虑 Agent-as-a-Service 化，提供标准化API给其他系统调用
