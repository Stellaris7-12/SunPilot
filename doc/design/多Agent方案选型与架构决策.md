# 多Agent架构后续演进方案：实时通话流 + A2A 解耦协作

> **文档用途：** 在现有"固定流水线 + 双轨混合"架构基础上，规划下一阶段的两条演进主线——**发单侧的实时通话流（ASR）** 与 **回单侧的 A2A 多Agent解耦协作**，作为项目从"可演示 Demo"走向"可接入真实场景"的架构蓝图。
>
> **创建日期：** 2026-07-28
> **文档定位：** 后续演进方案（Roadmap），非当前交付物
> **上游依据：** 第三次答辩意见（冷总 + Mentor，见 `doc/feedback/7.28第三次答辩意见.txt`）；实时通话链路设计（见 `doc/design/实时通话流式处理方案.md`）

---

## 〇、一句话概括

> **发单侧**用 ASR 把"通话结束后填单"变成"通话进行中实时填单"；**回单侧**用 A2A 把"每接一个系统就写一套耦合代码"变成"每个系统一个 Agent，回单 Agent 与它们对话取数、请求操作"。两条主线的共同内核是：**用 Agent 的语义能力，抹平 700+ 场景与多系统集成的开发成本。**

## 一、为什么要演进：从答辩意见还原真实诉求

### 1.1 评审给出的核心判断

| 来源 | 关键意见 | 推导出的架构诉求 |
|------|---------|----------------|
| 冷总（总经理） | 当前价值有限，**因为没接入真实场景** | 架构必须能低成本对接真实的行内多系统 |
| 冷总 | 后续形态：无UI、无人工介入的**全Agent自动化 + A2A 改造**，Agent 间低耦合 | 以 A2A 作为跨系统协作的骨架 |
| 冷总 | **A2A 是后续最有价值的改造方向**：一个业务系统一个 Agent，回单 Agent 与其他系统 Agent 直接沟通"要做什么、取什么信息"，从而解耦，免去繁重耦合开发 | 集成方式从"点对点硬编码"转向"Agent 对话" |
| Mentor | 行内现状：**发单侧已做**（通话记录→工单），**回单侧未做**（处理问题+反馈） | 回单侧是主战场，也是 A2A 的落点 |
| Mentor | **700+ 场景**业务流差异极大，几乎每个都要单写 Workflow；专用场景可纯规则匹配（正则），无需 LLM；想用 Agent 打通、降低开发量 | Agent 做"通用骨架 + 语义路由"，规则做"场景专用快车道" |
| Mentor | 金融合规**不允许完全无监督**，以**半监督**为主（Agent 执行 + 人工审核 + 弹窗确认） | 每个对外部系统的写操作都要有"授权闸门" |
| Mentor | 可用 **RAG** 让 Agent 决策前先检索规范/惯例 | 引入知识检索层增强场景表现 |
| Mentor | 发单侧进阶：**语音实时处理（ASR）**，Agent 依通话实时生成工单与处理意见 | 发单侧实时通话流 |

### 1.2 立场修正：从"暂不引入 A2A"到"以 A2A 为主线"

前一版本文档在 Demo 阶段给出的结论是"**不引入 A2A**"，理由是：五个 Agent 同进程、函数直调即可，跨进程协议是过度设计。**在两周单机 Demo 的边界内，这个判断是成立的**——它避免了为不存在的分布式需求付出协议成本。

但答辩意见把边界推到了真实生产：**回单 Agent 需要与行内多个独立业务系统交互**。此时"同进程函数直调"的前提消失了，原文档 3.2 节里已经埋好的那句话正式生效——

> "如果 TicketAgent 需要调用其他公司/部门的独立 Agent 服务……那时 A2A 才有价值。"

**那一刻已经到来。** 因此本方案不是推翻旧结论，而是接续它的触发条件：Demo 内保持同进程简单实现，生产化时按下面的路线切换到 A2A。

## 二、演进主线一：发单侧实时通话流（ASR）

> 详细链路、代码与答辩话术见 `doc/design/实时通话流式处理方案.md`，此处只做定位与要点提炼，避免重复。

### 2.1 从"通话后批处理"到"通话中流处理"

现状（发单侧已做）：坐席通话 → 生成通话记录文本 → 一次性喂给 Intake → 生成工单。这是**批处理**：信息完整才开工。

进阶（Mentor 指出的方向）：坐席通话进行中 → ASR 实时转写 → 增量喂给流式 Intake → **边听边填单、边听边给处理意见**。这是**流处理**：信息永远不完整，工单随对话逐步收敛。

### 2.2 为什么流处理正好凸显 LLM 价值

批处理场景下，确定性规则（正则/关键词）已能覆盖大部分抽取，LLM 更多是"锦上添花"。但流处理天然是**信息不完整**的：

- 对话刚开始只有半句话，字段大面积缺失；
- 客户表述口语化、乱序、有修正（"哦不对，是上个月"）；
- 需要在信息不全时就给出**概率性的初步判断**，并随新信息持续修正。

这正是**LLM 概率推理**相对确定性规则的核心优势区：规则要求"匹配到才输出"，LLM 可以"基于已有片段给出带置信度的推断，后续再确认或推翻"。因此实时通话流不是简单加个 ASR，而是让"双轨混合"里的**慢车道（LLM）从辅助变主力**。

### 2.3 与现有架构的衔接（不重写，复用）

| 现有能力 | 实时化改造点 |
|---------|------------|
| `Intake` 确定性抽取 + LLM 兜底 | 包成增量式 `StreamingIntakeProcessor`，每个 ASR 分片触发一次增量抽取 |
| `FieldState`（value/confidence/source/locked） | 直接复用：规则命中即 `locked`，LLM 只能填补空缺、不得覆盖已锁定值 |
| `/api/tickets/{id}/ai-process-stream`（SSE） | 新增 `/api/tickets/{id}/realtime-stream`，输入侧接 ASR 分片，输出侧沿用 SSE 逐字段推送 |
| 前端流式渲染 | 表单字段随置信度渐进填充、可视化"正在收敛"状态 |

**结论：实时通话流是对现有双轨架构的"输入侧实时化 + 慢车道加权"，而非另起炉灶。**

## 三、演进主线二：回单侧 A2A 多Agent解耦协作（重点）

### 3.1 问题的本质：集成成本，而非智能不足

回单侧的真实困难不在"AI 够不够聪明"，而在**集成**：一张工单要办结，往往要横跨核心系统、CRM、账务、风控、外部渠道等多个业务系统去查信息、做操作。传统做法是为每个系统写一套对接代码（接口协议、字段映射、鉴权、异常处理），这就是冷总说的"**繁重的耦合开发**"。

700+ 场景 × 多系统，点对点耦合的复杂度是**乘积级**的：新增一个系统或一个场景，都要改动大量既有对接代码。这是回单侧迟迟没做的根因。

### 3.2 A2A 的解法：把"系统对接"变成"Agent 对话"

冷总的设想可以精确表述为：

> **每个业务系统暴露一个自己的 Agent；回单 Agent 不再直连各系统的接口，而是与各系统 Agent 用统一协议对话——"我要办 XX，需要什么信息、要走什么流程，你来告诉我并代为执行"。**

这把集成的复杂度从**乘积级降为加法级**：

| 维度 | 点对点耦合 | A2A 解耦 |
|------|-----------|---------|
| 新接入一个系统 | 回单侧改 N 处对接逻辑 | 该系统上线自己的 Agent，回单 Agent **零改动**即可对话 |
| 字段/接口变更 | 回单侧跟着改映射 | 由系统 Agent 内部消化，对外契约不变 |
| 新增场景 | 可能触达多个系统对接层 | 回单 Agent 用语义描述意图，路由到相关系统 Agent |
| 协议 | 各系统各一套 | **统一 A2A 协议**（能力发现 + 消息交换 + 任务状态） |

### 3.3 A2A 目标架构

```
                        ┌─────────────────────────────┐
                        │      回单 Agent（编排方）      │
                        │  意图理解 / 任务分解 / 结果汇总  │
                        └───────────────┬─────────────┘
                                        │  A2A 协议
                                        │ (能力发现 · 消息 · 任务状态)
              ┌─────────────────┬───────┴────────┬──────────────────┐
              │                 │                │                  │
      ┌───────▼──────┐  ┌───────▼──────┐  ┌──────▼───────┐  ┌───────▼──────┐
      │ 核心系统 Agent │  │  CRM Agent   │  │  账务 Agent   │  │  风控 Agent   │
      │ (查账户/交易)  │  │ (查客户资料)  │  │ (发起冲正等)  │  │ (合规校验)    │
      └──────────────┘  └──────────────┘  └──────────────┘  └──────────────┘
        各系统自持其 Agent，内部如何实现（规则/LLM/存量接口）对回单侧透明
```

关键点：**每个系统 Agent 是它所属系统的"语义门面"**——对内封装该系统的存量接口与业务规则，对外只暴露统一的 A2A 能力描述。回单 Agent 只需理解"意图"，不需理解任何系统的内部实现。

### 3.4 A2A 协议的三块最小内核

参考社区 A2A（Agent Card / Task / Message）思路，落到本项目至少需要：

1. **能力发现（Agent Card）**：每个系统 Agent 声明"我能做什么"（如 `queryAccountBalance`、`initiateReversal`）、入参出参、以及**是否为高风险写操作**。回单 Agent 启动时拉取所有 Card，形成可路由的能力目录。
2. **消息交换（Message）**：回单 Agent 用自然语言 + 结构化意图发起请求；系统 Agent 返回数据或执行结果。允许多轮澄清（"要冲正哪笔交易？"）。
3. **任务状态（Task lifecycle）**：`submitted → working → input-required → completed / failed`。**`input-required` 是半监督合规的挂钩点**（见 3.6）。

### 3.5 与现有 Orchestrator 的关系：内层不变，外层新增

现有 `Orchestrator` 编排的是**同进程内**的五个业务 Agent（Classifier/Intake/Resolution/Escalation/Notification），这套"单工单内的处理流水线"**保持不变**。A2A 是在它之外增加的**跨系统协作层**：

```
回单 Agent（A2A 编排）
   └─ 对单张工单：调用现有 Orchestrator 完成分类/抽取/风险门/工具规划
        └─ 当 Resolution 规划出"需要外部系统执行"的动作时，
             不再走 Mock Tool，而是通过 A2A 调用对应系统 Agent
```

**演进映射**：现有的 `mock_executor` / `tool_registry` 正是 A2A 的天然占位——今天 Resolution 产出"工具调用计划"由 Mock 执行；生产化时，把"Mock 执行"替换为"A2A 消息发给系统 Agent 执行"，工具契约（`validate_tool_call`）平滑升级为 A2A 能力契约。**当前架构已经为 A2A 预留了接缝。**

### 3.6 半监督合规：A2A 与"人工审核 + 弹窗"如何结合

金融合规不允许全无监督，这与 A2A 并不冲突——**A2A 负责"能做"，审核闸门负责"准不准做"**：

- 系统 Agent 的每个**写操作能力**在 Agent Card 中标记 `requiresApproval: true`；
- 回单 Agent 发起此类操作时，A2A 任务进入 `input-required` 状态，前端弹窗："允许 Agent 在【账务系统】执行【交易冲正】吗？"（允许 / 不允许）；
- 人工点"允许"后，任务才从 `input-required → working`；
- 只读查询类能力无需弹窗，保证效率。

这与本项目既有边界完全一致：**自动化流程不得关闭工单**（仅 `POST /api/tickets/{id}/close`），NotificationAgent 只能给 `closureSuggestion.canClose`。A2A 沿用同一原则：**Agent 可执行、人工做最终闸门。**

### 3.7 RAG 增强：决策前先查规范

Mentor 建议决策前检索规范/惯例。在 A2A 链路中，RAG 挂在**回单 Agent 的意图理解与任务分解之前**：

```
工单意图 → RAG 检索(该场景的处理规范/历史惯例/合规要求) → 组装为决策上下文
        → 回单 Agent 分解任务 → A2A 分发给系统 Agent
```

RAG 让回单 Agent 在"要做什么、按什么规范做"上更贴合行内实际，而不是仅凭通用知识臆断。知识库可按场景/条线组织，与 700+ 场景目录对齐。

### 3.8 700+ 场景如何被"打通"

Mentor 的核心诉求是用 Agent 降低 700+ 场景的开发量。A2A + 分层设计给出的答案是**"通用骨架 + 专用快车道"**：

- **通用骨架（Agent 语义层）**：绝大多数场景共享同一套"意图理解 → RAG → 任务分解 → A2A 分发 → 半监督执行 → 汇总回单"的流程。新增场景主要是新增**知识（RAG 语料）+ 能力映射**，而非新写一套 Workflow 代码。
- **专用快车道（规则层）**：高频、流程固定的专用场景，仍可用纯正则/规则 Workflow 直连——**无需 LLM，最快最省**。这与现有"确定性快车道"一脉相承。
- **路由**：Classifier 判断场景 → 命中专用快车道走规则；否则落到通用 Agent 骨架。

这样 700+ 场景不再是"700+ 套代码"，而是"1 套骨架 + N 个规则快车道 + 一份可增长的知识库/能力目录"，**开发量从乘积级降为加法级**。

## 四、分阶段落地路线

> 原则：**Demo 内不为生产需求提前付费，生产化时按接缝平滑切换**。每一阶段都能独立交付价值。

| 阶段 | 目标 | 关键动作 | 验收信号 |
|------|------|---------|---------|
| **P0（现状）** | 单机 Demo 跑通 | 固定流水线 + 双轨混合 + Mock Tools | 通话记录→工单→自动处理→人工审核关闭 |
| **P1 实时通话流** | 发单侧实时化 | `StreamingIntakeProcessor` + `/realtime-stream` SSE + 前端渐进填充 | 通话进行中工单字段逐步收敛 |
| **P2 A2A 骨架（单系统）** | 打通第一个真实系统 | 定义 A2A 协议最小内核；把 `mock_executor` 替换为对 1 个系统 Agent 的 A2A 调用；写操作接弹窗审核 | 回单 Agent 通过 A2A 完成一次真实查询 + 一次受控写操作 |
| **P3 A2A 多系统 + RAG** | 多系统协作 + 规范增强 | 接入 2–3 个系统 Agent；能力目录 + 路由；RAG 语料按场景组织 | 一张工单跨系统办结，决策带规范检索 |
| **P4 场景规模化** | 700+ 场景覆盖 | 通用骨架 + 规则快车道分层；知识库/能力目录持续扩充 | 新增场景主要靠加语料/映射，代码改动趋近于零 |

**P1 与 P2 可并行**：实时通话流在发单侧，A2A 在回单侧，互不阻塞。

## 五、风险与边界

| 风险 | 说明 | 应对 |
|------|------|------|
| A2A 协议不成熟 | 社区标准仍在演进，各系统 Agent 由不同团队实现 | 先定**项目内最小契约**（Card/Message/Task 三件套），对齐后再逐步向社区标准靠拢 |
| 各系统 Agent 落地节奏不一 | 回单 Agent 就绪但对端系统没有 Agent | A2A 适配层做**降级**：无 Agent 的系统仍走存量接口/Mock，接口与 A2A 调用同签名 |
| 合规审计要求 | 每次跨系统写操作都需可追溯 | A2A 任务全链路留痕（意图、审批人、执行结果），沿用现有工单审计 |
| LLM 幻觉/误操作 | Agent 语义决策可能出错 | 半监督弹窗做最终闸门；写操作强制人工确认；只读操作可放开 |
| 实时通话流延迟 | ASR + LLM 增量推理的时延 | 规则快车道优先出结果，LLM 异步修正；置信度可视化让人工可介入 |

**不可逾越的边界（沿用现有约束）：**

- 自动化流程**不能关闭工单**，关闭只经 `POST /api/tickets/{ticket_id}/close`；
- 对外部系统的写操作**必须经半监督审核**；
- PageAgent 仍限白名单动作，A2A 是 PageAgent 的**升级替代**（有系统 Agent 时走 A2A，没有时才退回 PageAgent 做 UI 自动化兜底）。

## 六、答辩话术（一分钟版）

> "评审提到当前价值有限，因为没接真实场景，而 A2A 是最有价值的后续方向——我们完全认同，并把它定为架构主线。
>
> 我们的判断是：回单侧的真正难点不是 AI 不够聪明，而是**集成成本**——700 多个场景要横跨多个业务系统，点对点耦合是**乘积级**的开发量。A2A 把'系统对接'变成'Agent 对话'：**每个系统一个 Agent，回单 Agent 只表达意图，由各系统 Agent 自己决定怎么取数、怎么执行**，复杂度从乘积级降到加法级，新接一个系统回单侧几乎零改动。
>
> 合规上我们守住半监督：**Agent 能执行、人工做闸门**，每个写操作弹窗确认，这跟我们现在'自动化不能关单、只能建议关单'是同一条原则。
>
> 而且现有架构已经为它预留了接缝——今天 Resolution 产出工具计划、Mock 执行，生产化时把 Mock 换成 A2A 调用即可，工具契约平滑升级为能力契约。
>
> 发单侧我们同步做**实时通话流**：ASR 边听边填单，信息永远不完整，这恰恰是 LLM 概率推理压过确定性规则的地方。"
