## 一、业务背景与动机

### 1.1 真实客服场景

在实际信用卡客服业务中，坐席是**边接听电话边实时填写工单**的：

```
[电话接入]
    → 坐席实时听取 → 实时理解客户诉求 → 实时填写工单字段
    → 通话结束时工单已基本完成
    → 复核后提交
```

当前系统的处理模式是"**通话结束后提交完整摘要**"，与真实业务场景有差距。引入实时通话流式处理后，系统可以做到：

> **通话进行时，Agent 实时监听、实时提取、实时填单——坐席通话结束即可直接确认提交。**

### 1.2 这个场景为什么更有意义

- **演示价值：** 视觉冲击力显著高于"提交文本→等3秒→出结果"，通话文字逐字流出、表单字段实时填入更直观
- **架构论点价值：** 提供了一个真实场景，证明多Agent + LLM在特定条件下优于确定性规则（见下文分析）
- **贴近真实业务：** 面向金融行业评审，场景可信度高

## 二、流式场景下的架构优势分析

### 2.1 批处理 vs 流式：确定性规则的退化

| 场景 | 确定性规则快车道 | 多Agent + LLM |
|------|----------------|--------------|
| 字段尚未说完整（"交易在周末…"，日期未出现） | ❌ 规则需完整句子才触发 | ✅ LLM从上下文推断：大概率周六/周日，餐饮类 |
| 客户前半段说"查账单"，后半段改口"其实要退款" | ❌ 规则拿第一次分类定死 | ✅ ClassifierAgent在新信息到来时修订意图 |
| 关键字段分散在整个通话中 | ❌ 每条规则需独立触发 | ✅ LLM积累上下文，概率性填写并随信息完善 |
| 提前预判升级风险 | ❌ 只能通话结束后判断 | ✅ EscalationAgent实时监听，发现"投诉"立刻预警 |

### 2.2 核心论点

**批处理场景：** 完整通话记录 → 所有字段都在文本里 → 确定性规则效果极好，LLM只做兜底

**流式场景：** 增量文本持续到来 → 信息不完整 → 需要概率推断和状态维护 → **多Agent + LLM 优势最自然的展示舞台**

这与现有架构的"双轨混合"设计完全一致：
- 字段齐了 → 确定性通道（快）
- 字段不齐、信息模糊 → LLM通道（兜底）

流式处理让"字段不齐、信息模糊"变成了常态，因此 LLM 通道的价值更突出。

### 2.3 答辩对比论点

现场可以做两种模式的演示对比：

```
模式一：批处理（现有）
  提交完整通话摘要 → 确定性规则一次性提取全部字段 → 3秒出结果
  → 说明：规则在完整信息时效率极高

模式二：实时流式（新增）
  通话逐句流入 → Agent实时推断部分字段 → 表单渐进填入 → 通话结束工单已完成
  → 说明：不完整信息时LLM推断接管，多Agent协作展现真实价值
```

## 三、技术设计

### 3.1 整体架构

```
[模拟通话发生器]
      │  SSE / WebSocket，每0.5-1秒推送一句话
      ▼
[POST /api/tickets/{id}/realtime-stream]
      │  增量文本 chunk
      ▼
[StreamingIntakeProcessor]
      │  维护 partial_context，增量更新字段
      ├── 规则抽取（当前chunk）
      └── LLM推断（必填字段不齐时）
      │
      ▼
[SSE → 前端 SunPilot 面板]
      │  field_update 事件
      ▼
[前端表单渐进式填入动画]
```

### 3.3 增量 Intake 处理器（核心）

**关键设计：带置信度的字段状态机**

```python
class FieldState:
    value: Any
    confidence: float        # 0.0 - 1.0
    source: Literal["rule", "llm_inferred", "llm_confirmed"]
    locked: bool             # True = 确定性提取，不允许覆盖

class StreamingIntakeProcessor:
    """
    维护增量通话上下文，每次新chunk到来时：
    1. 先跑确定性规则（当前chunk + 完整累积上下文）
    2. 若必填字段仍有缺口，触发LLM对累积上下文做推断
    3. 输出 field_update 事件（仅输出本次新增/变更的字段）
    """

    def __init__(self, scenario_config: ScenarioConfig):
        self.accumulated_text = ""
        self.field_states: Dict[str, FieldState] = {}
        self.required_fields = scenario_config.required_fields

    async def process_chunk(self, chunk: str) -> List[FieldUpdate]:
        self.accumulated_text += chunk
        updates = []

        # 第一步：确定性规则
        rule_result = extract_deterministic(self.accumulated_text)
        for field, value in rule_result.items():
            if field not in self.field_states or not self.field_states[field].locked:
                updates.append(self._update_field(field, value, "rule", 1.0, locked=True))

        # 第二步：LLM推断（仅当必填字段有缺口时）
        missing = [f for f in self.required_fields
                   if f not in self.field_states or self.field_states[f].confidence < 0.7]
        if missing:
            llm_result = await self._llm_infer(self.accumulated_text, missing)
            for field, (value, confidence) in llm_result.items():
                existing = self.field_states.get(field)
                # LLM不允许覆盖已锁定的确定性值
                if not (existing and existing.locked):
                    updates.append(self._update_field(field, value, "llm_inferred", confidence))

        return updates  # 只返回本次变更，前端增量更新
```

**置信度策略：**

| 来源 | 置信度 | 是否锁定 | 可覆盖条件 |
|------|--------|---------|-----------|
| 确定性规则提取 | 1.0 | ✅ 是 | 不可覆盖 |
| LLM高置信推断（>0.85） | 0.85+ | ❌ 否 | 可被规则或更高置信LLM覆盖 |
| LLM低置信推断（<0.85） | <0.85 | ❌ 否 | 可被任何新信息覆盖 |
| 前端手动填写 | 1.0 | ✅ 是 | 不可覆盖（人工优先） |

### 3.4 新增后端接口

```python
# POST /api/tickets/{ticket_id}/realtime-stream
# Body: {"chunk": "客户说交易是上周五晚上在一个餐厅", "session_id": "xxx"}
# Response: SSE 流，field_update 事件

@router.post("/{ticket_id}/realtime-stream")
async def realtime_stream(ticket_id: int, body: ChunkInput):
    processor = get_or_create_processor(body.session_id, ticket_id)
    updates = await processor.process_chunk(body.chunk)

    async def generate():
        for update in updates:
            yield f"data: {update.model_dump_json()}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")
```

### 3.5 前端渐进式填入

**SunPilotPanel.vue 新增事件处理：**

```typescript
// 监听 field_update SSE 事件
onFieldUpdate((update: FieldUpdate) => {
  // 1. Agent时间线新增一步：「Intake提取 ${update.field}」
  addTimelineStep({
    agent: 'IntakeAgent',
    action: `提取字段：${update.field}`,
    value: update.value,
    confidence: update.confidence,
    source: update.source
  })

  // 2. 对应表单字段高亮 + 打字动画填入

  typewriterFill(update.field, update.value)

  // 3. LLM推断的字段用虚线边框标注（区分确定性提取）

  }
})
```

**视觉区分：**
- 确定性提取 → 绿色实线边框 + ✅ 图标
- LLM高置信推断 → 橙色实线边框 + 🤖 图标
- LLM低置信推断 → 橙色虚线边框 + ⚠️ 图标（需坐席确认）

## 五、答辩话术

### 开场引入

> "在真实客服场景中，坐席是一边打电话一边实时填单的——通话记录本身是流式产生的，不是一次性交给系统的完整文本。我们基于这个观察，增加了实时通话处理链路。"

### 技术对比论点

> "这个场景揭示了一个有意思的现象：在批处理模式下，确定性规则效果很好，LLM只是兜底；但在流式场景下，信息始终是不完整的——客户可能先说了'上周'，过了10秒才说'交易金额'，规则没有完整句子就无法触发。这时候LLM的概率推断价值才真正体现出来，系统可以先用已有信息做最大可能的推断，随着通话进行持续修正，而不是等通话结束才开始处理。"

### 亮点强调

> "这让我们的双轨混合架构在两个维度都有了演示案例：完整信息时走确定性快车道（高效低成本）；不完整信息时走LLM慢车道（兜住长尾）。通话结束时，工单基本已填完，坐席只需要复核——我们叫它'零秒发单'。"

## 六、与现有架构的关系

| 特性 | 批处理（现有） | 实时流式（新增） |
|------|-------------|----------------|
| 输入形式 | 完整通话摘要 | 增量文本chunk |
| 规则快车道触发条件 | 必填字段全部抽到 | 单chunk内有完整字段 |
| LLM介入频率 | 低（规则够用） | **高**（字段常不完整） |
| 字段完成时机 | 处理完成后 | **通话进行中实时填入** |
| 坐席等待时间 | ~3秒（通话后） | **约等于0**（通话中已完成） |
| 演示视觉效果 | 提交→等待→出结果 | **表单实时填入动画** |
| Agent展示价值 | 中 | **高** |
