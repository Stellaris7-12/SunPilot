# SunPilot 信用卡工单智能处理引擎 —— 方案 · 原理 · 方法详解

> 面向答辩/交接的技术说明文档。所有机制、字段、状态、配置结构均取自真实代码
> （`ai-engine/`），非 PPT 营销口径。数字口径请以实测为准。

---

## 0. 一句话定义

SunPilot 是一套把**电话工单从非结构化输入，自动处理到"可结案"状态**的多 Agent 引擎：

- **理解**：把电话录音转写等非结构化内容，归一化为标准工单并识别场景意图；
- **执行**：内部系统走 **API 直连**、外部无接口系统走 **PageAgent 页面代填**（双轨制）；
- **合规**：五个 Agent 节点独立审计、全链路 `trace` 留痕，**自动流程永远不能自己结案**，
  结案只能由人工经 `POST /api/tickets/{id}/close` 完成。

一句话记忆点：**"确定性优先、双轨执行、人工闭环"**。

---

## 1. 总体方案：三大设计决策

整个系统的设计可以浓缩为三个相互支撑的决策，后面的原理都是围绕它们展开的。

| 决策 | 解决什么问题 | 怎么落地 |
|------|------------|---------|
| **① 确定性优先 + LLM 兜底** | LLM 不稳定、金融场景要可控 | 规则/正则先抽字段（快车道），缺字段才调 LLM 补空（慢车道），**LLM 绝不覆盖确定值** |
| **② 双轨制执行** | 内外部系统接入方式异构 | 内部系统 API 直连；外部无接口系统用 PageAgent 语义化/DOM 代填 |
| **③ 合规不可自动结案** | 金融操作要可追溯、要人把关 | 五节点独立审计 + `trace_steps` 留痕 + 状态机强制人工确认闭环 |

这三点不是并列的技术点，而是一条逻辑链：
**因为要可控（①），所以有确定性快车道；因为系统异构（②），所以有双轨；
因为是金融场景（③），所以再快也要人工闭环。**

## 2. 系统架构（四层）

自顶向下的数据流：

```
交互接入层   电话转写 → Vue3 工作台(SunPilot 侧边栏) → FastAPI 网关(SSE 流式)
    │
编排层       Orchestrator.process_ticket()  ·  PipelineContext 贯穿  ·  StateMachine
    │        高危短路 → ①Classifier → ②Intake → ③Escalation → ④Resolution → ⑤Notification
    │
能力执行层   五 Agent(共享 AsyncOpenAI 客户端)  |  轨道一:工具执行链  轨道二:PageAgent
    │
基座层       业务 LLM(DeepSeek) · 页面 LLM(Qwen) · workflow_config.json · MySQL+traces
```

### 关键代码位置

| 层 | 模块 |
|----|------|
| 编排 | `orchestrator/orchestrator.py`（`process_ticket`）、`pipeline_context.py`、`state_machine.py` |
| Agent | `agents/{classifier,intake,escalation,resolution,notification}_agent.py`，基类 `agents/base.py` |
| 工具 | `tools/registry.py`（`validate_tool_call`）、`tools/mock_executor.py`（`execute`） |
| 配置 | `ai-engine/data/workflow_config.json` + `orchestrator/workflow_config.py` |
| 接口 | `main.py`（`/ai-process-stream`、`/reply-draft`、`/close`、`/llm/proxy/*`） |

## 3. 编排原理：process_ticket 的真实执行序

`Orchestrator.process_ticket()` 是整个引擎的主脊。真实顺序（源自代码，非简化）：

1. **加载工单 + 建 PipelineContext**，捕获入口原始状态 `entry_status`
   （必须在改状态前捕获，否则快照重入判断失效）。
2. 状态切 `IN_PROGRESS`。
3. **高危短路**：`ticket.risk_level == HIGH` 直接 `_handle_high_risk` 返回，不进流水线。
4. **快照重入判断**：若存在快照且入口状态是 `pending_info` / `pending_human_confirm`，
   则**跳过 Classifier**（意图不变），只重跑 Intake 抽取补充信息；否则走正常流程。
5. **① Classifier**：意图分类 → `_normalize_pipeline_intent` 场景归一化。
6. **② Intake**：确定性抽取优先，缺字段才 LLM 兜底（见 §4）。
7. **字段补全** `_run_field_enrichment`。
8. **③ Escalation**（风险闸门）`_run_escalation_step`（见 §5）。
9. **提前停止判断** `_maybe_stop_before_resolution`：命中则停在
   `PENDING_INFO` / `PENDING_HUMAN_CONFIRM` 并存快照返回。
10. **④ Resolution**：按意图取候选工具 `tool_registry.list_for_intent`，生成工具计划；
    `UNKNOWN` 场景启用 LLM 工具选择兜底。
11. **工具校验 + 执行**：`tool_registry.validate_tool_call`（契约校验）
    → `mock_executor.execute`（原子操作 + trace）。
12. **执行后复评**：再跑一次 `_run_escalation_step`（结果可能触发升级）。
13. **⑤ Notification** + `_finish_review`：置 `PENDING_HUMAN_REVIEW`，产出结案建议。

> 记忆点：**Escalation 跑两次**（执行前闸门 + 执行后复评），这是"边界追问"常考点。

### PipelineContext 与 public_result

- 所有 Agent 的输入/输出都挂在一个 `PipelineContext` 上顺序流转，避免各 Agent 各自持有零散状态；
- 返回给前端前用 `public_result()` **剥离 `_` 前缀的内部键**，只暴露对外字段。

## 4. 原理①：确定性优先 + LLM 兜底（Intake 核心）

这是全系统最能体现"工程判断"的一块，位于 `agents/intake_agent.py`。

### 快车道（deterministic）

```
1. _deterministic_fields(): 按场景字段，依次尝试
   结构化解析 → extractRule 正则 → 带置信度的兜底抽取
2. _missing_required(): 对照场景 required_fields，算出仍缺哪些必填字段
3. 若 已抽到字段 且 无必填缺失 → 直接返回，extraction_mode="deterministic"
   （不调用任何 LLM）
```

`extractRule` 是配置里声明的正则，例如"调单扣款"场景：

```json
{ "name": "callerNo", "label": "主叫号",
  "extractRule": { "type": "regex", "pattern": "(1\\d{10})" } }
```

### 慢车道（llm_augmented）

只有当**必填字段有缺口**时才触发：调 LLM 抽取 → `_merge_fields` 合并。合并规则是本方案的**红线**：

```python
# LLM only fills gaps, never overrides real values
- 确定性已抽到真实值的字段：保留，LLM 不得覆盖
- 确定性为空 且 LLM 抽到值：用 LLM 值补上
- 字段是否"为空"由 _is_present() 判定（"未提供"/"null" 等都算空）
```

### 为什么这么设计

| 好处 | 说明 |
|------|------|
| 可控可追溯 | 身份证/金额/单号等高确定性字段走规则，结果稳定、可复现，满足金融审计 |
| 省成本省延迟 | required 全命中时 **0 次业务 LLM 调用**，快车道端到端约 3s |
| LLM 只做它擅长的 | 只在非结构化文本缺口处补全，不参与状态/证据/闭环决策 |

> 一句话答辩：**"LLM 是兜底补空的，不是拍板的。状态、证据、能否结案全由确定性逻辑掌控。"**

## 5. 原理②：风险闸门（Escalation Guards）

位于 `agents/escalation_guards.py`，是一组**确定性 Guard**（非 LLM 判断），按序短路：

| Guard | 触发条件 | 结果 |
|-------|---------|------|
| `unsupported_scene` | 意图 = `UNKNOWN` | 未接入自动化工具 → 建议转人工，`can_auto_proceed=False` |
| `missing_required` | 必填字段仍缺失 | `needs_more_info=True` → 停在 PENDING_INFO |
| `high_risk_ticket` | 风险 = high | 已拦截 → 转人工审核 |
| `requires_confirmation_before_tool` | 中风险 或 场景标 `requires_human_confirmation` | 待人工确认 → 停在 PENDING_HUMAN_CONFIRM |

场景是否需要人工确认，由配置 `requires_human_confirmation` 声明（单一事实源），而非硬编码。

## 6. 原理③：双轨制执行

统一编排层根据目标系统类型分流：

| | 轨道一 · API 直连 | 轨道二 · PageAgent 代填 |
|--|------------------|------------------------|
| 适用 | 内部系统（核心账务/卡片/额度） | 外部无开放接口系统 |
| 机制 | REST/RPC 标准契约 → `validate_tool_call` → `mock_executor.execute` | 语义化动作协议 / DOM 白名单动作 |
| 人工 | 全自动，约 3s | **提交前拦截 + 强制人工确认**，约 10s |
| 约束 | 全链路 trace 留痕 | 仅白名单页面动作，禁止任意 DOM-index 点击 / JS 执行 / 直接保存关单 |

**PageAgent 三范式选型**（作为佐证，不展开）：视觉感知（重、慢） / DOM 索引 ReAct（通用、鲁棒） /
语义化动作协议（快、廉、稳，仅限自有前端）→ **最终双范式混合**：外部走 DOM 索引，自有前端走语义化协议。

---

## 7. 原理④：合规闭环（不可自动结案）

这是金融场景的硬约束，也是与通用 RPA 的关键区别：

- **五节点独立审计**：五个 Agent 输入/输出/决策全程 `trace_steps` 留痕，可回放；
- **NotificationAgent 只出建议**：`closure_suggestion.can_close` 仅当
  `status == pending_human_review` 且工具执行 `success` 时才为 `True`——**它只建议"可否结案"，不能触发结案**；
- **结案唯一入口**：状态机走到 `PENDING_HUMAN_REVIEW`，人工经 `POST /close` 才真正关单；
- 状态机全集：`open / in_progress / pending_info / pending_human_confirm /
  pending_human_review / escalated / failed / cancelled / closed`。

## 8. 配置即单一事实源

`ai-engine/data/workflow_config.json` 驱动全流程，顶层结构：

```
default_workflow          默认场景
commonFields (5)          通用字段
scenarios {协商还款/伪冒预防/伪冒调查/客户经营/市场企划/调单扣款/征信/UNKNOWN}
```

每个场景包含：`fields` / `specificFields`（含 `extractRule` 正则）/ `required_fields`
/ `recommended_tool` / `candidateTools` / `detection`（意图识别关键词+优先级）
/ `requires_human_confirmation` / `notification_template`。

> 设计约束：**不得再引入与配置竞争的硬编码字段映射**。改字段/场景/门控只改这一个文件，
> 经 `WorkflowConfig.model_validate(...).to_runtime_dict()` 校验后生效（camelCase → snake_case）。

## 9. 两套 LLM 的边界

| | 业务 Agent | PageAgent / SunPilot |
|--|-----------|---------------------|
| 配置前缀 | `LLM_*` | `PAGE_AGENT_LLM_*` |
| 网关/模型 | DeepSeek 兼容网关，`deepseek-v4-flash` | Ali/Qwen，`qwen3.7-plus` |
| 调用方式 | 后端直连 | 经后端代理 `/api/llm/proxy/*` |

按需异构：业务决策用擅长中文的 DeepSeek，页面/工具类交互用 Qwen，两套配置严格隔离。

## 10. 答辩速记（三句话）

1. **原理**：确定性优先抽字段、缺口才用 LLM 兜底补空，LLM 不覆盖确定值也不拍板。
2. **架构**：五 Agent 顺序编排 + 双轨制执行（内部 API / 外部 PageAgent），配置单一事实源。
3. **合规**：五节点独立审计、全链路 trace、自动流程不可自动结案，人工 `POST /close` 才闭环。
