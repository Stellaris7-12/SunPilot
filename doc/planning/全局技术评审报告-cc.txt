SunPilot 工单智能处理引擎 —— 技术评审报告
评审结论速览
代码工程质量扎实：确定性 fast-lane、防 LLM 幻觉的确定性覆盖、"仅人工结案"边界、fail-fast 配置加载都做得对。但方案文档（7.26-11方案总结.md）与代码实现存在系统性偏差——文档把若干"愿景/单点能力"描述成了"已落地架构"。评审要害集中在三点："双轨制"架构在代码里不存在、配置驱动只覆盖了声明式元数据、PageAgent 的安全白名单在 ReAct 通道下整体失效。

一、最严重的偏差：方案宣称的"双轨制"在代码中不存在
方案的核心卖点是"轨道一（内部系统 API 直连，不引入 PageAgent）/ 轨道二（外部遗留系统，PageAgent 走 ReAct 探索）"。我在整个后端做了检索验证：

没有任何 track / system-type 分流逻辑。全代码库找不到 is_external、has_api、轨道、system_type 之类的分支判断。orchestrator.py:106-309 的 process_ticket 是单一固定流水线，不存在"按系统可接入性走不同轨道"的决策点。
所谓"API 直连"其实是 mock。工具执行统一走 mock_executor.py:30，其 docstring 自述 "Simulates external business APIs"。没有真实内部系统 API 调用。
PageAgent 操作的是本应用自己的 Vue 表单，不是外部遗留系统。所有 page_task 动作的 target 都是内部语义 id：orchestrator.py:1084-1128 的 page-agent-reply-draft、enterprise-reply、sunpilot-fields；main.py:600-637 的 dispatch-<field>、draft-submit。这些是 SunPilot 自身表单元素，不存在"探索未知外部系统 DOM"的场景。
pageHints/轨道/ReAct 在后端只出现于一条注释（config.py:49），无实现。
结论：真实架构是"单轨：5 Agent 管道（工具为 mock）→ 生成面向自家 Vue 表单的半语义 PageTask → 前端 SunPilot 填单，坐席确认"。ReAct 引擎确实存在（fork 自阿里 page-agent），但它当前也只作用于自家表单的自由文本兜底，并未用于任何外部系统。"API 优先、UI 兜底、70%/30% 占比"是设计愿景，不是当前代码形态。 这是对外汇报时最大的表述风险——一旦评审方看代码，双轨叙事无法自证。

技术可行性：不需要推翻重来
关键是你已有的架构完全可以承载这三个改造：

Pydantic schema 可以加嵌套的 detection/extractRule/workflow_params 字段。
load_workflow_config 已经把配置全量加载到内存，运行时访问无性能问题。
当前代码里已经在按字段名/场景名做分发，只是分发表硬编码在 Python——你要做的是把这张表挪到 JSON，分发逻辑改成 table-driven。
我给个最小改造路径（2-3 天工作量，不动现有业务逻辑）：

阶段一：场景检测规则外置（先啃最硬的骨头）
在 WorkflowScenario 加一个字段：

class WorkflowScenario(ApiModel):
    # ... 现有字段
    detection: Optional[Dict[str, Any]] = None  # {"patterns": [...], "keywords": [...], "priority": int}
修改 normalize_scene（scenario_detection.py:99）：

def normalize_scene(raw_scene: str) -> str:
    config = load_workflow_config()
    # 按 priority 排序，串行匹配
    for scenario in sorted(config["scenarios"].values(), key=lambda s: s.get("detection", {}).get("priority", 999)):
        detection = scenario.get("detection")
        if not detection: continue
        # 动态构建正则
        patterns = detection.get("patterns", [])
        if any(re.search(p, raw_scene) for p in patterns):
            return scenario["workflow_name"]
    return "UNKNOWN"
把现有 7 个场景的正则从 _SCENE_PATTERNS 照抄到 workflow_config.json 的 detection.patterns。
工作量：1 天（schema + 迁移逻辑 + 把现有正则搬进 JSON）。风险：低，现有场景行为不变，只是数据源换了。

阶段二：字段抽取规则外置（解决 elif 链）
specificFields 加 extractRule：

class FieldDefinition(ApiModel):
    name: str
    label: str
    type: Optional[str] = "text"
    extract_rule: Optional[Dict[str, Any]] = None  # {"type": "regex", "pattern": "..."}
新建通用抽取器：

def extract_by_rule(field_name: str, rule: dict, transcript: str, context: dict) -> Optional[str]:
    rule_type = rule.get("type")
    if rule_type == "regex":
        return _first_match(rule["pattern"], transcript)
    elif rule_type == "structured":
        return context.get(field_name)  # 从 LLM merge 结果取
    elif rule_type == "lookup":
        return context.get(rule["source_field"])
    return None
_draft_ext_json 重构为循环：

def _draft_ext_json(transcript, scenario_config, llm_context):
    ext = {}
    for field in scenario_config.get("specific_fields", []):
        rule = field.get("extract_rule")
        if rule:
            ext[field["name"]] = extract_by_rule(field["name"], rule, transcript, llm_context)
    return ext

阶段三：补强校验 + 文档（稳固基础）

三阶段改完后的效果
新增场景：在 JSON 里加一个 scenario block（detection patterns + fields + extractRule + template），0 行代码变更。
700 场景扩展瓶颈消失：配置文件拆成目录结构（data/scenarios/repayment_negotiation.json），每个场景独立维护。
运营可以安全维护：配置有强校验（forbid extra + 交叉校验），改错会在加载时 fail；extractRule 是声明式的，运营看文档就能写正则/选 type。
对比"推翻重来"方案
如果你说"配置驱动彻底失败，我们改用 LLM 自由抽取所有字段"：

丢掉确定性 fast-lane：现在低风险场景 0 次 LLM 秒级返回，改成全 LLM 后每工单至少 3-5 秒 + 成本 × 5。
丢掉字段契约：当前 required_fields 清单保证了下游一定能拿到这些键；改成自由抽取，下游要写一堆 .get(key, default) 防护，且 LLM 可能幻觉出不存在的字段名。
700 场景更难维护：每个场景的 prompt 是长文本，比 JSON 配置更难 diff、review、版本管理。
所以**"配置驱动"这条路本身是对的**，只是你现在走了 30%（声明式元数据）就停了，剩下 70%（行为规则外置）没做。

我的建议
