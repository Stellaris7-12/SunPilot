## 二、架构改进总结

### 1. 从"编排者独裁"到"Agent 自主决策"

**改造前**:
```python
# 编排器霸凌：即使 EscalationAgent 说可以自动通过，编排器依然强制暂停
if risk_level == "medium" and not ctx.confirmed:
    return await self._pause(...)
```

**改造后**:
```python
# 完全信任 EscalationAgent 的 LLM 决策
if not can_auto_proceed:  # can_auto_proceed 来自 EscalationAgent
    return await self._escalate(...)
# 删除了硬编码的中风险强制暂停
```

**价值**: EscalationAgent 现在可以根据客户画像（VIP等级、历史交易）和工单金额综合决策，而非粗暴的风险等级一刀切。

---

### 2. 从"工具失败即放弃"到"故障自愈"

**改造前**:
```python
if not tool_result.success:
    return await self._escalate(ctx, failure_reason, ...)  # 直接投降
```

**改造后**:
```python
if not tool_result.success:
    # 让 ResolutionAgent 通过 LLM 分析错误并修正参数
    retry_result = await self._run_agent_step(self.tool_agent, retry_input, ...)
    # 如果 LLM 给出了修正后的参数，重新执行
    tool_result = await mock_executor.execute(retry_tool_name, retry_tool_params)
    # 重试仍失败才升级
```

**价值**: 可拦截"日期格式错误"、"参数缺失"等 60%+ 的可修正错误，减少无效人工工单。

---

### 3. 从"硬编码规则"到"配置驱动"

**改造前** (场景检测):
```python
# scenario_detection.py 硬编码
_SCENE_PATTERNS = (
    ("伪冒预防", ..., re.compile(r"非本人申请|冒名|伪冒预防|...")),
    ("伪冒调查", ..., re.compile(r"伪冒调查|卡片被.*管制|...")),
    # ... 7个场景写死
)
```

**改造后**:
```json
// workflow_config.json 配置驱动
{
  "伪冒预防": {
    "detection": {
      "patterns": ["非本人申请", "冒名", "伪冒预防", "..."],
      "priority": 1
    }
  }
}
```

**价值**: 新增场景只需运营在 JSON 中添加配置，不需要开发介入。

---

### 4. 从"重复计算"到"增量恢复"

**改造前**:
```python
# PENDING_INFO 恢复时，从头运行 Classifier 和 Intake（重复消耗 Token）
intent_result = await self._run_agent_step(self.classifier_agent, ...)
extract_result = await self._run_agent_step(self.intake_agent, ...)
```

**改造后**:
```python
# 检查快照，有则跳过
snapshot = await pipeline_context_repository.get_snapshot(ticket_id)
if snapshot and ticket.status in ("pending_info", "pending_human_confirm"):
    intent_result = snapshot["intent_result"]
    extract_result = snapshot["extract_result"]
    # 跳过 Classifier 和 Intake LLM 调用
```

**价值**: PENDING_INFO 恢复时省 2 次 LLM 调用，杜绝意图漂移（第一次判"退款"，第二次可能判"咨询"）。

## 七、关键决策记录

### 决策1: 保留确定性 fast-lane

**背景**: 评审建议"LLM 优先，规则兜底"，但当前是"规则优先，LLM 填空"。

**决策**: **保持规则优先**。理由：
- 低风险场景 0 次 LLM 秒级返回，改成全 LLM 后每工单 3-5 秒 + 成本 ×5
- 字段契约（required_fields）保证下游一定能拿到这些键
- 配置驱动的 extractRule 已实现规则外置，新增场景零代码

**Trade-off**: LLM 在规则未覆盖时才介入，但通过 P2-10 已实现规则可配置化。

### 决策2: 故障自愈只重试一次

**背景**: 工具失败后可以无限重试。

**决策**: **只重试一次**。理由：
- 避免无限循环（如 LLM 幻觉参数）
- 60%+ 的错误是参数格式问题，一次修正足够
- 重试仍失败说明是业务规则问题，需要人工介入

**Trade-off**: 复杂错误可能需要多次重试，但可通过提升 LLM prompt 质量改善。

### 决策3: 配置热加载失败时保留旧缓存

**背景**: 配置重新加载失败可能导致服务不可用。

**决策**: **失败时保留旧缓存**。理由：
- 避免配置错误导致服务停摆
- 返回 500 错误提示运营修正配置
- K8s 滚动重启期间不会出现新旧配置并存导致数据不一致

**Trade-off**: 运营看到 500 错误后需要修正配置再重试，但比服务宕机好。
