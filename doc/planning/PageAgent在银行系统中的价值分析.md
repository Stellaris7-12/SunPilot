# PageAgent 在银行系统中的价值分析与答辩话术

> 面向答辩/汇报场景，说明 PageAgent（非侵入式页面代操作）在银行等强监管、强隔离环境中的真实价值、边界与话术。
> 核心立场：**对能对接的系统走 API 确定性通道；对够不着的长尾外部系统走 PageAgent 非侵入代填。** 主动承认边界，反而更可信。

---

## 一、核心结论

会存在"无法开发 / 无法调 API 来填表"的成熟系统，而且在银行领域很常见。

关键认知纠偏：**"无法对接"几乎从来不是"这个系统技术上没有 API"，而是"这个 API 对你不可达"。** 而"成熟"与"可达"是两回事——在银行，很多时候系统越核心、越成熟，反而越不可达。

因此 PageAgent 的定位不是"比 API 对接更强"，而是：**在对接不可行 / 来不及 / 不值得时，当天就能让流程跑起来，并由人工把最后一道高风险操作关卡守住。**

---

## 二、为什么成熟的银行系统反而"够不着"

不是系统做得差，而是下面这几堵墙：

### 1. 安全隔离墙（银行最典型）
- 银行核心系统、信贷系统、反洗钱系统通常跑在**生产内网 / 涉密网**，安全策略明令禁止对外开放接口。
- 人只能坐在终端前手工操作——这不是"没做 API"，而是"制度上不允许有对外 API"。
- 对这类系统，任何"外部程序直连"的方案都过不了安全评审；而 PageAgent 在坐席已登录的浏览器内、以人的身份操作，不新增对外暴露面。

### 2. 组织 / 行政墙
- 系统有 API，但归属另一个部门 / 另一个厂商。要用得走跨部门审批、安全评审、厂商合同、按调用量付费。
- 技术上一天的事，流程上可能走半年。**"API 存在" ≠ "你能用"。**

### 3. 厂商锁定的采购系统
- 银行大量系统是采购来的、非自研。厂商可能给 API，但覆盖不全（UI 能做的功能 API 只覆盖一部分）、要企业版加钱、要认证成为合作伙伴。
- 偏偏关键流程只有 UI 有入口。

### 4. 对接 ROI 不划算（长尾问题）
- 需要交互的往往不是 1 个系统，而是一长串下游 / 外部系统。
- 让平台与每一个都做 API 对接根本不现实，于是操作员只能把数据手工重录进各系统——这正是 PageAgent 代填的教科书场景。

### 5. 上线速度
- API 对接要对方配合开发、联调、部署，受制于人。
- 驱动 UI 不用求对方，像人一样点击填写即可，可当天上线。

---

## 三、银行场景中的典型落地案例

| 场景 | 为什么够不着 API | PageAgent 的价值 |
|---|---|---|
| 工单 / 派单转下游单位 | 各接单单位（分行、外包催收、外部机构）各有各的系统，无法逐一对接 | 非侵入代填工单，零对接成本 |
| 反洗钱 / 风控核查系统 | 涉密内网，禁止对外接口 | 坐席登录态下代填查询条件、汇总结果 |
| 政务 / 征信 / 公积金查询 | 第三方成熟系统，无公开 API 或需高门槛准入 | 以人的身份代填查询、抓取结果回工单 |
| 老旧信贷 / 账务终端 | 遗留系统，改造冻结、无 API | 代填录入，替代人工重复录入 |
| 采购来的第三方 SaaS | API 覆盖不全 / 需加钱 / 需准入认证 | 补齐 UI 能做但 API 做不到的操作 |

## 四、这不是自我感动——一整个行业在为它付费

- UiPath、Automation Anywhere、Blue Prism，以及国内的影刀、来也（Laiye）、阿里云 RPA，整个 **RPA 赛道的存在，就是"因为够不着 / 不划算而去驱动 UI"这一需求的证明**。
- 而 RPA 最大的买家恰恰是**银行、电信、政府**——这几个行业同时具备"系统多、隔离强、对接难、合规重"的特征。
- PageAgent 可以理解为 **"RPA + LLM 语义理解"**：传统 RPA 靠录制固定坐标/脚本，脆且难维护；PageAgent 靠 LLM 读懂页面字段语义再填，对 UI 变化更鲁棒。

---

## 五、必须主动承认的边界（诚实反而加分）

答辩时**主动讲这部分**，比被评委追问出来更可信：

1. **只要 API 对你可达，就该用 API。** PageAgent 是兜底和过渡，不是"比 API 更好"。
2. **它有固有代价**：依赖对方 UI（对方改版可能失效）、速度慢于 API、不适合高吞吐批处理、依赖坐席登录态。
3. **高风险动作必须人工把关**：保存、提交、结案等操作在系统中被安全策略阻断（`BLOCKED_CLICK_TARGETS`），只能由坐席人工确认，PageAgent 不自动提交。
4. **不硬上**：若目标系统既有源码又能自由调 API，对它用 PageAgent 就是纯技术债，应老实做对接。

## 六、答辩话术

### 6.1 一句话定位（电梯陈述）
> "对能对接的系统，我们走 API 确定性通道；对够不着的长尾外部系统——典型就是各接单单位和涉密内网系统——我们用 PageAgent 非侵入代填，**零对接成本、当天上线、人工把最后一道提交关**。"

### 6.2 若被问"为什么不直接调 API"
> "如果 API 对我们可达，我们当然优先用 API，系统里确定性通道就是干这个的。但在银行，很多核心系统跑在涉密内网、制度上不允许对外开接口，人只能在终端手工操作；还有大量下游单位系统各不相同、逐一对接 ROI 不成立。PageAgent 正是为这部分'够不着的系统'兜底——它在坐席已登录的浏览器里，以人的身份操作，不新增任何对外暴露面。"

### 6.3 若被问"这跟传统 RPA 有什么区别"
> "传统 RPA 靠录制固定坐标和脚本，页面一改就崩、维护成本高。PageAgent 用大模型读懂页面每个输入框的语义（label / placeholder / name），再把业务字段映射进去，对 UI 变化更鲁棒。可以理解为 RPA 的 LLM 升级版。"

### 6.4 若被问"安全性 / 会不会乱操作"
> "三层约束：第一，高风险操作（保存、提交、结案）在代码层被阻断列表拦截，只能人工确认，Agent 不会自动提交；第二，内部系统走白名单语义目标，不允许按 DOM 索引乱点；第三，整个过程坐席全程可见、可随时接管。Agent 只做'代填 + 定位',最后一道关永远是人。"

### 6.5 若被问"成熟系统怎么会没有 API"
> "'成熟'和'可达'是两回事。政务的税务、社保、公积金系统都很成熟，但对外部往往没有可用 API；银行核心系统更是制度上禁止对外接口。系统成不成熟决定不了它对我们开不开放——决定因素是安全策略、组织归属、厂商合同和对接成本。"

### 6.6 收尾升华
> "我们不是要用页面自动化取代系统对接，而是承认现实：在银行这种强隔离、强监管、系统林立的环境里，**总有一批系统你短期内对接不上，但业务今天就要办**。PageAgent 填的就是这道缝——让坐席从机械重录里解放出来，把精力放在判断和复核上。"

## 七、一页速记（背诵版）

- **定位**：能对接走 API，够不着才上 PageAgent。
- **为什么够不着**：涉密内网禁接口 / 跨部门审批 / 厂商锁定 / 长尾对接不划算 / 上线要快。
- **典型场景**：派单转下游单位、风控核查、政务征信查询、老旧账务终端。
- **行业背书**：RPA 赛道百亿市场，最大买家就是银行电信政府。
- **与 RPA 区别**：LLM 读语义，比录制脚本更鲁棒。
- **边界**：脆 / 慢 / 不做高吞吐 / 高风险动作人工确认 / API 可达就别硬上。
- **安全**：阻断列表 + 白名单 + 全程可接管，最后一道关永远是人。

## 八、真实部署形态：PageAgent 在外部系统里以什么形式存在

### 8.1 决定形态的唯一约束

PageAgent 干活靠的是**拿到目标页面的 DOM**（`document.querySelector`、遍历 `document.body`、`input_text` 按索引填）。所以问题本质是一句话：

> **agent 代码怎么才能跑进"外部系统那个页面"的 DOM 上下文里？**

当前它内嵌在自家 Vue SPA 里，只能操作同源同页的 DOM。外部系统是别的域名 / 别的进程，同源策略挡死——够不着。因此"存在形式"这个问题，等价于"用什么载体把 agent 注入到别人的页面里"。

### 8.2 几种真实形态与取舍

| 形态 | 怎么拿到外部 DOM | 优点 | 代价 / 风险 | 银行适配度 |
|---|---|---|---|---|
| **浏览器扩展（content script）** | 浏览器授权，注入脚本到任意网页 | 直接拿真实 DOM、现有代码几乎复用、以坐席身份跑、不新增对外暴露面 | 需装扩展、过 IT 审批、企业策略分发 | ⭐ 最高 |
| **桌面悬浮窗（独立原生 App）** | 拿不到 DOM，靠 OS 无障碍 API / 图像识别定位控件 | 跨浏览器、可操作 C/S 客户端 | 脆（认坐标 / 截图）、传统 RPA 老路、维护重 | 中（需操作非浏览器客户端时才值） |
| **后端浏览器自动化（Playwright/Puppeteer）** | 服务器起真浏览器开外部系统 | 无人值守、可批处理 | 服务器需持有外部系统凭据——银行合规几乎必然卡死 | 低（涉密内网基本禁止） |
| **Electron/CEF 内嵌浏览器外壳** | 外部系统在可控浏览器壳里打开 | 完全可控、可注入 | 要求用户改用你的壳访问外部系统，落地成本高 | 中低 |

### 8.3 对本项目的结论

**浏览器扩展（content script）是唯一顺理成章的答案：**

1. **代码几乎能复用**：现有 PageAgent 就是操作 `document` 的 JS，content script 本质就是把同一套代码注入到别人的页面。dom_tree、tools、编号识别框、SunPilot 面板基本原样搬。
2. **"悬浮窗"是它的 UI 形态、不是对立选项**：扩展可往目标页面注入一个浮动面板 / 侧边栏，这就是"桌面悬浮窗"的观感。**载体是浏览器扩展，呈现是注入式悬浮面板，二合一。**
3. **合规上最站得住**：以坐席已登录的身份、在他自己的浏览器里操作，不把凭据交给服务器、不新增对外暴露面——银行安全评审最认这一点。后端 Playwright"服务器替你登外部系统"的方案在银行几乎必死。
4. **独立桌面 App 只有一个场景才值**：当要操作的不是网页、而是 C/S 架构的桌面客户端（很多银行老终端是这种）。那时没有 DOM，只能走 OS 无障碍 API / 图像识别，即退回传统 RPA 机器人——重且脆，除非确有桌面客户端要接，否则不碰。

### 8.4 一句话回答"这东西怎么装到外部系统上"

- **网页类外部系统** → 浏览器扩展 + 注入式悬浮面板（现有代码演进，首选）。
- **桌面客户端类** → 独立桌面 App + OS 级自动化（传统 RPA，重，按需）。
- **后端 Playwright** → 银行合规红线，基本排除。

结论：**是浏览器插件；悬浮窗是插件注入的 UI，不是另一条路。**
