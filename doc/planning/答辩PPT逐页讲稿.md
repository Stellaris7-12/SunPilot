## 第 4 页：总体架构（1.5 分钟）★ 核心页

**内容**：架构图——业务大脑 + 执行手 + 通信通道

```
业务大脑（后端 5 Agent）  →  SSE / PageTask  →  执行手（前端 PageAgent）
  分类+提取+校验+工具+回单                     填表+回单+证据+动画
         ↕                                          ↕
   workflow_config (700+ 场景配置)           SimulatorMask + Panel
```

**讲述**：
"系统的核心架构是两层 AI 协作。后端五个 Agent——分类、提取、校验、工具选择、回单生成——负责所有业务决策，我们叫它'业务大脑'。前端 PageAgent 负责在页面上执行操作——填表、点按钮、定位证据，我们叫它'执行手'。

两个大脑之间的通信通道有两种模式：快车道走 PageTask 结构化协议，慢车道走自然语言 observation。

最关键的设计：700+ 场景的差异不在代码里，在 workflow_config.json 里。每个场景一条配置——登记了它有哪些字段、每个字段在页面上对应哪个元素。新增场景就是加一条 JSON，Agent 代码不动。"

## 第 5 页：后端多 Agent 管道（1 分钟）

**内容**：5 个 Agent 的职责和数据流

| Agent | 输入 | 输出 | LLM调用 |
|-------|------|------|---------|
| Classifier | 工单原文 | 场景类型 | 一次 |
| Intake | 原文+场景 | 字段列表 | 一次 |
| Escalation | 字段+风险 | 通过/暂停/升级 | 规则为主，LLM兜底 |
| Resolution | 场景+字段 | 工具+参数 | 一次 |
| Notification | 全流程结果 | 回单+通知 | 一次 |

**讲述**：
"每个 Agent 只做一件事。分类 Agent 判断这是什么场景，提取 Agent 抽取结构化字段，校验 Agent 检查风险和完整性，工具 Agent 选择并调用业务工具，回单 Agent 生成客户回复。每个 Agent 可以独立优化 Prompt、独立评测。

校验 Agent 内部还拆成了三个 Guard 模块——完整性检查、风险评估、工具结果判断——大部分逻辑是确定性规则，不需要调 LLM。所以全流程 LLM 调用只有 3-4 次。"

## 第 6 页：PageAgent 方案选择（1.5 分钟）★ 调研亮点

**内容**：三条调研路线对比

| 路线 | 方式 | 问题 |
|------|------|------|
| 自研 LLM Planner | 后端生成计划，前端执行 | LLM 看不到 DOM，蒙眼决策 |
| npm 安装阿里 page-agent | 引入通用网页 Agent | 每步调 LLM，太慢；定制受限 |
| **fork 源码裁剪** | 复制核心引擎，自建适配层 | 完全控制，适配 Vue |

**讲述**：
"PageAgent 这部分我们调研了三条路线。

第一条是自研：后端 LLM 生成操作计划，前端按计划执行。但 LLM 看不到页面 DOM——它只能根据寥寥几个上下文字段猜测按钮在哪。这是'蒙眼决策'。

第二条是直接用阿里开源的 page-agent：npm 安装，一行 import。但它每操作一步就要调一次 LLM，一个表单填下来 15-30 秒。而且它是为通用网页设计的，我们自己的 Vue 页面不需要'探索'。

第三条是我们最终选的——把 page-agent 的源码拿过来，裁剪掉不需要的部分，保留核心引擎。这样我们既有 ReAct 循环的完整能力，又能完全控制工具白名单和 UI 样式。整个裁剪过程涉及 22 个源文件，核心循环 661 行完全复用，我们自己新增了约 200 行适配代码。"

## 第 7 页：PageAgent 分层执行（1 分钟）

**内容**：快车道 vs 慢车道

```
快车道（已知 Vue 页面）:  PageTask 结构化指令 → 确定性执行 → 0 次 LLM
慢车道（未知外部页面）:   自然语言 observation → ReAct 自主探索 → 5-10 次 LLM
```

**讲述**：
"PageAgent 有两层执行模式。

对于我们自己写的 Vue 页面——表单、回单编辑器、证据区——我们走快车道。后端 Agent 处理完后，直接输出一份 PageTask 结构化指令：'把回单填到 target=reply-editor，把证据定位到 target=evidence-panel'。前端执行器按指令逐条执行，不调 LLM，每步 400 毫秒。

对于外部遗留系统——那些我们没有源码、改不了 DOM 的页面——才启用 ReAct 慢车道。LLM 自己观察页面、自己理解结构、自己决策操作。每步 2-5 秒，慢但能处理没见过的页面。

当前 demo 中，Vue 页面完全用快车道。ReAct 能力保留在代码库里，外部系统接入时直接激活。"

## 第 8 页：700+ 场景泛化方案（1 分钟）★ 架构核心

**内容**：配置驱动的场景差异

```
新增场景 = 1 条 workflow_config JSON + 表单模板加 data-page-agent-target
Agent 代码：0 行改动
执行器：0 行改动
```

**现场展示**：打开 workflow_config.json，展示 5 个场景的特有字段定义

**讲述**：
"700+ 场景不需要 700 套代码。这是一条 workflow_config 配置。

伪冒预防场景有 10 个特有字段——CALLID、投诉人信息、案件编号。市场企划场景只有 6 个特有字段——卡片名称、订单号、客户反馈。征信场景有 4 个——账户类型、是否敏感、逾期状态。

表单引擎是同一个 v-for 循环——根据场景类型动态渲染不同的字段组合。发单 Agent 是同一个——根据配置提取不同的字段。新增一个场景只需要增加一条 JSON 配置，运营团队可以维护，不需要开发介入。"
