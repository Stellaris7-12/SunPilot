# TicketAgent 答辩 PPT 大纲

> 2026-07-23，预计 15 页，15 分钟

## 一、背景与痛点（3 页）

### 1.1 业务规模
- 招商银行信用卡工单：330 万件/年，700+ 业务场景
- 涉及 300+ 部室、近万名员工
- 单张工单从发单到回复平均 30 小时
- 数据来源：132 张工单模板下 44 个字段，71% 来自业务系统接口，29% 需人工补充

### 1.2 核心痛点
- 发单侧：坐席在 13 个业务系统间切换，手动复制粘贴客户数据
- 回单侧：回复依赖个人经验，质量参差不齐，高频工单仍需逐单人工判断
- 700+ 长尾工单尚未完成业务系统嵌入，发单效率极低

### 1.3 项目目标
- 试点阶段：发单效率提升 60%，节省人力 70 人/年
- 全量阶段：80% 一键发单，处理时长缩短 40%

## 二、方案设计（5 页）

### 2.1 总体架构：双脑协作
- 业务大脑（后端多 Agent）：分类、提取、校验、工具调用、回单生成
- 执行手（前端 PageAgent）：页面操作、鼠标动画、步骤展示
- 通信通道：SSE bridge + observation / PageTask 协议
- 架构图展示

### 2.2 后端多 Agent 管道
- 5 个 Agent 各司其职：Classifier → Intake → Escalate → Resolve → Notify
- 每个只做一件事，独立优化 Prompt，独立评测
- EscalationAgent 拆为三个 Guard 模块（CompletenessGuard / RiskGuard / ToolResultGuard）
- LLM 调用：试点 3 场景 2-3 次，全量 700+ 场景 3-4 次（不随场景数增长）

### 2.3 PageAgent：从调研到落地
- 调研三条路线：自研 LLM Planner → 阿里 page-agent npm → fork 源码裁剪
- 最终选择：fork Ali page-agent 核心引擎（PageAgentCore + PageController + SimulatorMask）
- 定制：Vue Panel + SSE bridge + LLM proxy
- 快车道（pageHints 确定性执行）+ ReAct 兜底（未知场景）

### 2.4 700+ 场景的泛化方案
- 核心：配置驱动，而非代码驱动
- workflow_config.json：每个场景一条配置（字段定义 + target 映射 + 必填校验）
- 新增场景 = 加一条 JSON 配置 + 表单模板加 target 属性，Agent 代码零改动
- 5 个真实场景差异展示：伪冒预防 vs 伪冒调查 vs 市场企划 vs 客户经营 vs 征信

### 2.5 数据流与关键设计决策
- PipelineContext：类型化上下文替代松散 dict
- PageTask 协议：结构化执行指令替代自然语言猜测
- Mock 系统：独立于工单的外部系统模拟（Agent 不感知数据来源）
- 三层降级：确定性执行 → LLM ReAct → 人工接管

## 三、Demo 演示（2 页）

### 3.1 发单侧完整链路
- 坐席选择通话记录（5 种场景各一）
- 发单Agent 自动识别场景 + 提取字段
- 表单自动切换为该场景的特有字段组合
- PageAgent 可见填表（鼠标动画 + 步骤展示）
- 提交 → 工单创建 → 自动跳转回单处理台

### 3.2 回单侧完整链路
- 坐席点击"AI 处理" → Panel 实时展示 5 个 Agent 进度
- 处理完成 → 自动填入回单 + 定位证据 + 滚动复核区
- 低风险场景可自动结案，高风险场景停人工确认

## 四、创新点与技术亮点（2 页）

### 4.1 架构创新
- 双脑解耦：业务决策与页面执行分离，通过 PageTask 协议通信
- 配置驱动泛化：700+ 场景 ≠ 700 套代码，而是一个引擎 + 700 条配置
- 分级协作：快车道（确定性执行，0 次 LLM）+ ReAct 兜底（未知页面，5-10 次 LLM）

### 4.2 工程亮点
- Ali page-agent 源码裁剪：保留 ReAct 循环 + W3C 标准 DOM 操作，去除 React/Chrome Extension 等冗余，适配 Vue 生态
- 5 种真实企业场景的差异化表单（基于招商银行 FITS 系统 50 张截图 OCR 提取）
- Mock 系统分层：Agent 不感知 Mock/真实接口边界
- 完整审计链路：trace_steps + tool_call_log + agent_execution_log + page_action_logs

## 五、结果与量化指标（1 页）

- 发单效率：从手动填表 5 分钟 → AI 自动填表 30 秒
- LLM 调用优化：从每步 ReAct 5-10 次 → 确定性执行 0 次（已知场景）
- 场景泛化验证：5 类真实场景，配置驱动全自动切换
- 数据库：MySQL 演示沙盘，15 张表覆盖业务、审计、Mock 域、评测

## 六、反思与后续（1 页）

### 当前不足（主动说明）
- Mock 数据独立化未完成：当前从工单样本抽取，架构抽象层已正确
- PolicyLayer 安全层未实现：MVP 放弃白名单 + 风险分级，后续阶段补齐
- 真实 13 系统对接未验证：当前用 Mock 层隔离，架构为替换预留了接口
- Schema 校验未全量启用：框架已建，生产环境必须开启

### 后续规划
- 第一阶段：Mock 数据独立化 + PolicyLayer 安全层
- 第二阶段：全量 700+ 场景配置覆盖（运营团队维护 JSON）
- 第三阶段：接入外部遗留系统（PageAgent ReAct 兜底价值体现）

## 七、总结（1 页）

> "这套系统的核心价值不在"能填多少个表单"，
> 而在"架构设计让新增场景只需要加配置，不需要改代码"。
>
> 我们用 5 个场景验证了架构的泛化能力，
> 用 fork Ali page-agent 搭建了页面执行引擎，
> 用双脑解耦解决了业务决策和页面操作的职责分离。
>
> 700+ 场景不是 700 套代码，是 700 条 JSON 配置。
> 这是可扩展架构的意义。"
