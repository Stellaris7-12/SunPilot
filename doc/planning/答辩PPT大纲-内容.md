## P04 · 业务背景与痛点

**规模背景：**
- 年处理工单量 **330万+件** · 业务场景 **700+个** · 原平均处理时长 **24小时以上**

**痛点 → 解决措施（一一对应）：**

| 业务痛点 | 解决措施 |
|---------|---------|
| 工单字段繁多、结构多变，人工提取慢 | 配置驱动 + 确定性优先，规则先行、LLM兜底 |
| 内外系统割裂，无统一处理入口 | 双通道执行架构，同一决策大脑服务两条执行路径 |
| 外部系统无对外接口，靠人工重复填写 | PageAgent代填外部页面，坐席确认后提交 |
| 金融场景要求全链路可追溯、不可乱关单 | 5个独立Agent节点留痕，闭环必须人工确认 |

> 一句话：痛点决定了系统必须是「多Agent决策 + 双通道执行 + 全程可审计」。

## P05 · 方案调研与选型

**围绕三个关键选型，都不是技术偏好，是业务约束倒逼的结论：**

**① 编排框架：手写 PipelineContext（不用 LangGraph / AutoGen）**
- 工单处理是确定性线性DAG，不需要图路由和多Agent协商
- 金融合规要求状态转换完全可预测、可审计；框架版本迭代快，生产风险不可接受
- 约百行代码清晰表达整个流程，零框架依赖

**② 页面操作：场景感知的双范式（由「是否拥有目标UI」决定）**

| 范式 | 定位依据 | 用在哪 |
|------|---------|--------|
| DOM索引 + ReAct | DOM节点位置，LLM动态分析 | 外部系统（无API、无改造权限） |
| 语义化标签 | 稳定业务语义ID，对布局变化免疫 | 自有Vue前端（拥有开发权） |

- 基于成熟开源浏览器操作引擎（MIT协议）二次开发：裁剪冗余模块、复用ReAct核心、面向工单场景做适配集成

**③ 决策策略：确定性优先 + LLM兜底**
- 规则/schema先提取，字段全命中走快车道（发单仅1次LLM调用，约3秒）；缺失时LLM只填空缺、不覆盖已提取值
- 渐进式确定性化：新场景先走LLM，积累样本后固化为确定性通道

## P06 · 系统架构设计（五层架构图）

> 本页为一张完整的五层架构图，自上而下：

**① 接入层**
- SunPilot前端实时流光面板 · PageAgent浏览器扩展 · SSE流式输出

**② 编排层**
- Orchestrator 编排器 · PipelineContext 共享上下文 · 高风险短路 / 风险门控 / 人工确认停顿点

**③ Agent层（5个业务Agent，均继承BaseAgent + AgentCard）**
- Classifier → Intake → Escalation → Resolution → Notification

**④ 执行层（双通道）**
- 通道一：内部系统 API直连（Mock Tools审计 + tool_registry校验）
- 通道二：PageAgent代填外部页面（确定性语义执行为主 + ReAct兜底，坐席确认后提交）

**⑤ 数据与配置层**
- workflow_config.json（场景/字段/门控单一事实来源） · TDSQL持久化 · 两套LLM配置（业务DeepSeek / PageAgent Qwen）

> 强调：5Agent决策大脑在两条轨道上完全复用，业务逻辑不重复；配置是单一事实来源。

## P07 · 典型场景剖析——伪冒调查全流程

**场景：** 客户来电称卡片被系统管制、两核身不过。属于高风险伪冒调查场景，需查证卡片管制状态并发单至调查组。系统从通话录音到给出处理结果，端到端走一遍：

1. **录音转标准工单** → 通话文本进入处理管道
2. **Classifier** 识别意图，命中「伪冒调查」场景（关键词：卡片被管制 / 两核身 / X-DK / BLOCK）
3. **Intake** 确定性提取客户号、卡片列表、管制原因、X-DK编号等字段（缺失字段交LLM补全，不覆盖已提取值）
4. **Escalation** 风险评估——伪冒调查为高风险场景，命中风险门控，强制转人工确认
5. **Resolution** 规划工具调用，`tool_registry` 校验后执行卡账户状态查询等
6. **执行分通道：**
   - 通道一（内部系统）：调用 `card.account-status-query` 查卡片管制状态 → 结果写回工单，约3秒
   - 通道二（外部系统）：PageAgent打开调查组发单页面、语义填写工单 → **坐席确认后一键提交**，约10秒
7. **Notification** 生成回单建议，输出 `closureSuggestion.canClose`（系统不自动关单）
8. **人工审核关闭**：坐席核验管制原因与调查组处理意见后 `POST /close`，闭环完成

**时效对比：** 原人工流程 24小时+ → 系统处理 3–10秒

## P09 · 创新点与总结

**创新点一：双通道执行架构（核心）**
- 同一套5Agent决策大脑，服务内部API直连 + 外部PageAgent代填两条路径
- 业务约束倒逼的架构决策：覆盖场景更广，外部系统零接入成本、零侵入

**创新点二：配置驱动 + 确定性优先的处理管道**
- workflow_config.json 单一事实来源；规则先行、LLM只填空缺，渐进式固化
- 兼顾准确性、成本与可维护性，规避LLM幻觉风险

**创新点三：全链路合规可审计**
- 5个独立Agent节点各自留痕，trace可追溯
- 系统不可自动关单，闭环必须人工确认，符合金融风控要求

**项目成果：**
- 处理时效 24小时+ → 3–10秒 · 内外系统统一入口 · 全链路留痕

**当前局限（主动说明）：**
- 基于录音文件处理，暂不支持实时通话流式输入
- PageAgent依赖浏览器环境，不适用于纯API或桌面客户端系统

**技术规划：**
- 实时通话流式处理，工单在通话中增量填写
- A2A协议标准化接入，实现跨条线Agent通信
- Agent权限与安全控制层，统一管理自动化边界
- 建立评测基准量化各Agent表现，引入RAG对接行内知识库

- 学会在约束条件下做权衡：不是选最新的技术，而是选最适配业务场景的方案

**② 建立系统思维——先抓最重要的20%**
- 一开始想把所有功能都做完美，后来意识到必须先跑通核心链路
- 确定性提取 + 双通道架构 + 风控门控，这三个抓住了，系统骨架就立起来了

**④ 技术之外的成长**
- 学会主动沟通需求边界，而不是闷头实现后发现方向偏了
- 遇到卡点不钻牛角尖，快速验证 MVP、失败了就换方案

**未来决心：**
- 把这次的局限（实时流式、量化评测、成本分析）逐一补齐，让系统真正达到生产级标准

- 把"业务约束倒逼技术选型"这套思路带到后续工作中——技术是工具，解决问题才是目的
