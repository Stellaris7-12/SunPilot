# ai-engine 多 Agent 编排框架审查报告

> 审查对象：`ai-engine/` 后端五 Agent 管道与编排器
> 对照方案：`doc/planning/7.26-11方案总结.md`
> 日期：2026-07-26

---

## 一、总体评价

这套框架的**核心设计判断是正确且成熟的**：把 700+ 场景的工单处理拆成「确定性流向的五节点管道 + 配置单一真相源 + 确定性 fast-lane 兜住 LLM slow-lane」。相比方案文档里对标的 LangGraph 图编排，手写 `PipelineContext` 在这个 DAG 形态的业务里是**恰当的减法**——链路可读、可控、可审计，没有为复杂度买单。

方案文档的三大卖点在代码里**基本落地**：

| 方案主张 | 代码印证 | 结论 |
|---|---|---|
| 配置驱动泛化（引擎×1 + 配置×N） | `load_workflow_config()` + `WorkflowConfig.model_validate().to_runtime_dict()`；场景检测、字段抽取、工具选择、回单话术均从 config 读取 | ✅ 真实落地 |
| 确定性优先、LLM 只补空 | Intake 的 fast-lane 门控（必填全命中不调 LLM）+ `_merge_fields` 只填空缺 | ✅ 到位 |
| 自动流不结案，只建议 canClose | 关单唯一入口 `POST /close`；NotificationAgent 仅写 `closureSuggestion.canClose` | ✅ 边界清晰 |
| 全链路可观测 | trace_steps / tool_call_log / agent_execution_log / page_action_log 四类审计齐备 | ✅ 完整 |

**幻觉防护是这套代码最扎实的地方**：Classifier（场景枚举白名单 + workflow_name 固定）、Resolution（工具名白名单 + 参数清洗 + "勿编造"提示）、Notification（evidence_ids 只取真实工具证据、失败态强制模板）、Intake（LLM 不覆盖确定性值 + 上下文窗口校验）——四个 LLM 出口都有确定性护栏兜底。这是把 LLM 用在生产工单流里的正确姿势。

但审查也发现**一条高危缺陷、一处安全边界回退、以及若干与"单一真相源"原则相悖的死代码/双轨遗留**，详见下文。方案文档 §9.1 自评的四个"待补全项"（Agent 可能过度拆分、PolicyLayer 缺失、ReAct 待验证、Schema 未全量启用）与代码现状**吻合**，说明团队对自身短板判断准确。

## 二、主要业务流转过程总结

编排全部集中在 `orchestrator.py:process_ticket()`（`orchestrator.py:86-418`），单一大 `try/except` 包裹，任何异常坍缩为 `FAILED`。正常路径如下：

```
加载配置 + 工单
   │
   ├─[高风险短路] ticket.risk_level==HIGH → 伪造 verify → _escalate() → ESCALATED（跳过全部 5 Agent）
   │
   ├─[快照重入] 若 status∈(pending_info, pending_human_confirm) → 从快照取 intent（跳过 Classifier），仅重跑 Intake
   │
   ▼
① ClassifierAgent  分类：诉求 → FITS 场景（确定性正则命中则不调 LLM；纯咨询直接 UNKNOWN）
   ▼  归一化意图 _normalize_pipeline_intent
② IntakeAgent      提取：确定性抽取；必填全命中→fast-lane 返回，否则 LLM 只补空缺
   ▼
   字段补全 _run_field_enrichment（查 recommended_tool → mock_executor.enrich_params）
   ▼
③ EscalationAgent（第一次）风控：3 Guard（完整性/风险/合规）确定性短路 → 仅 medium/需确认才调 LLM
   ▼
   [门控 _maybe_stop_before_resolution]
      needs_more_info → PENDING_INFO（存快照，提前返回）
      can_auto_proceed==False → ESCALATED（提前返回）
   ▼
④ ResolutionAgent  工具规划：FITS 场景走 config recommended_tool（不调 LLM）；UNKNOWN 才 LLM 选工具
   ▼
   validate_tool_call（类型校验）→ 缺参 → PENDING_INFO
   ▼
   mock_executor.execute → 持久化 tool_call
   ▼
③′ EscalationAgent（第二次）复核工具结果
   ▼
   [升级判定] 工具失败 or can_auto_proceed==False → ESCALATED
   ▼
⑤ NotificationAgent 回单：确定性 fallback 话术 + LLM 润色，_normalize_result 强制护栏
   ▼
_finish_review() → PENDING_HUMAN_REVIEW（自动流正常终态，等待坐席复核结案）
```

**终态状态**：`PENDING_INFO` / `PENDING_HUMAN_REVIEW` / `ESCALATED` / `FAILED`。
（注：`PENDING_HUMAN_CONFIRM` 已不再由主流程主动产生，仅作为快照重入入口保留——见问题 §四.2。）

**上下文传递**：Agent 之间**不直接对话**，Orchestrator 是唯一中枢，`PipelineContext`（纯 dataclass）承载 `intent_result/extract_result/verify_result/tool_result` 等，每步把上游 dict 投影成下游 `*Input` 契约。ticket 被投影成 summary/resolution/risk/notification 四种视图。

## 三、高危问题（需优先修复）

### 🔴 P0-1：工具失败自愈重试分支是**必崩死代码**

`orchestrator.py:338` 用 `ctx.get("_tool_retry_attempted")`、`orchestrator.py:343` 用 `ctx["_tool_retry_attempted"]=True`，以 **dict 风格访问** `PipelineContext`，但它是纯 `@dataclass`（`pipeline_context.py:14-31`），**没有 `.get()`/`__getitem__`/`__setitem__`**。

后果：**任何一次工具执行失败**，都会在 `orchestrator.py:338` 抛 `AttributeError` → 被外层 `except` 捕获 → `FAILED`。这意味着：
- 方案文档 §3.2 "P1-7 故障自愈重试"从未真正生效；
- 工具失败本应走的"正常升级 ESCALATED"路径也被这个异常抢先劫持成 `FAILED`，**升级机制在工具失败场景下失效**。

叠加第二处 bug：`orchestrator.py:364-369` 的 `_run_agent_step` 调用签名错误（传 `(self.tool_agent, retry_input, trace, push)`，实际签名是 `(agent_id, agent_name, agent, input_data, trace, push)`）。两处叠加证明该分支**从未被测试覆盖执行过**。

**建议**：给 `PipelineContext` 增加一个显式字段 `tool_retry_attempted: bool = False` 并改用属性访问；修正 `_run_agent_step` 调用；补一个"工具失败"的 smoke 场景锁死回归。

### 🔴 P0-2：唯一关单入口 `POST /close` 已移除鉴权

`main.py:1183-1184` 注释 "Authentication temporarily removed to unblock frontend"。`auth.py` 的 `verify_admin_key` **当前只保护 `/config/reload`**（`main.py:1270`），而它注释里声明的保护对象正是 close 端点（`auth.py:25`）。结果：**任何人可无鉴权关任意工单**——这直接击穿 CLAUDE.md "自动流不能关单、关单只经受控入口"的核心边界。

**建议**：close 端点至少挂回 `Depends(verify_admin_key)`；生产前替换为方案 §9.2 规划的 session 鉴权。

## 四、与"配置单一真相源"原则相悖 / 双轨遗留

1. **死代码 `MINIMAL_WORKFLOW_CONFIG`**（`workflow_config.py:19-38`）：定义了兜底 config 但加载失败直接 `raise`，从不降级——保留误导性常量。
2. **`PENDING_HUMAN_CONFIRM` 半废弃状态**：主流程已删除"中风险强制暂停"硬编码（`orchestrator.py:634-640`），该状态只在快照重入判断被消费，产生它的代码路径已不存在，形成"只能进不能出"的悬空状态。
3. **场景检测双轨并存**：P2-9 已把规则外置到 `config.detection.patterns`，但 `scenario_detection.py:91` 的硬编码 `_SCENE_PATTERNS`、`LEGACY_*` 别名表仍在，大部分成死代码。
4. **两套缓存不一致**：`workflow_config` 用可热重载的手写锁缓存，`semantic_targets` 仍用不可重载的 `@lru_cache`（`semantic_targets.py:84`）——热重载 workflow 时语义 target 不同步刷新。
5. **快照生命周期缺失**：`pipeline_context_repository.py:79` 的 `delete_snapshot` 全项目**无调用点**，PENDING 工单快照永久残留（工单一般只置 CLOSED 不删，`ON DELETE CASCADE` 不触发）。
6. **文档与代码偏差**：CLAUDE.md 称 `reply_agent.py`/`intent_agent.py` 为兼容 shim 文件，实际这些文件**不存在**，legacy 别名是 `orchestrator.py:80-84` 的属性赋值。

## 五、契约与健壮性问题

- **契约非权威**：`IntakeResult`/`RiskDecision`/`ToolPlan` 等 Pydantic 契约存在，但 Agent `run()` 实际返回**裸 dict**，靠 orchestrator 的 `coerce_*` 事后校正；Agent 还私自返回契约外键（Intake 的 `extraction_mode`）。**NotificationAgent 输出无任何 Pydantic 契约**（裸嵌套 dict），是五个 Agent 里唯一未建模的出口，回归风险最高。
- **EscalationAgent 的 LLM 分支护栏最弱**（`escalation_agent.py:107`）：直接采信 `llm_result` 的 `risk_level`/`can_auto_proceed`/`additional_checks`，**无枚举白名单校验**，LLM 可把 high 降为 low 放行本应转人工的工单；且 `ESCALATION_SYSTEM_PROMPT` 里 `can_auto_proceed` 示例恒为 `true`，诱导模型偏向放行。这是五个 Agent 中唯一"LLM 能松风控闸门"的地方，与整体"确定性兜底 LLM"风格不符。
- **风险闸门 `max_risk` 在主执行路径未启用**：`orchestrator.py:249-254` 调 `validate_tool_call` 时未传 `max_risk`，`registry.py:233` 的风险白名单形同虚设。
- **副作用夹带**：`_field_enrichment` 通过给业务 fields dict 塞 `_`-前缀键传递（`orchestrator.py:464`）；重试控制信息塞进 `ticket["_previous_tool_failure"]`（`orchestrator.py:358`）绕过契约校验——这类"下划线私货"破坏了 schema 校验意图。
- **异常粒度过粗**：整个 `process_ticket` 一个大 `try/except Exception`，Agent 错误、DB 错误、上面的 AttributeError 统一坍缩为 `FAILED`，丢失了本可走 ESCALATED/PENDING_INFO 的可恢复性区分。
- **状态转移非法仅告警跳过**（`orchestrator.py:881-888`）不抛错，`ticket.status` 可能与预期静默不一致产生漂移。

## 六、Agent 拆分与职责评价

方案 §9.1 自问"Agent 是否过度拆分"——我的判断：**五个的拆法是合理的**，每个职责单一、边界清晰，且大多有确定性快车道可绕开 LLM（Classifier/Intake/Escalation/Resolution 都能在确定性命中时零 LLM 调用）。真正值得优化的不是数量，而是：

- **风险判定分散**：`risk_level` 来源不单一（ticket 预设值 vs 3 Guard vs LLM），EscalationAgent 又被调用两次承担"信息门控"和"工具结果复核"两种职责。可考虑把风险策略收敛为一个显式 PolicyLayer（也正是方案 §9.2 的规划），让风险来源单一化。
- **标签映射两处**：Intake 的 `_GLOBAL_LABEL_TO_NAME`（`intake_agent.py:164`）与 config 派生标签并存，宜统一进 config。

## 八、一句话结论

**架构方向对、幻觉防护扎实、配置驱动真实落地，是一套值得继续投入的工程**；但当前存在一条会让"工具失败即整单 FAILED、升级机制失效"的高危死代码，以及关单入口无鉴权的边界回退，这两条必须在任何生产/演示前修复。其余为死代码清理、契约收口、风险策略集中化，属于健康度改进，与团队自评的待补全项方向一致。
