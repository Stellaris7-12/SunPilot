# 方案选择答辩话术

> **答辩核心原则**：每个技术选型都能说出"我调研了 X 方案，因为[原因]放弃了它，选了 Y"。  
> 答辩时承认对立声音比只说好的更显深度。

---

## 一、开场定调

**话术：**

> "在方案选型上，我们这个项目面临三个有代表性的技术决策点：第一，**多Agent编排框架的选择**——是否采用 LangGraph、AutoGen 等主流框架；第二，**Agent 间协作协议的选择**——是否引入 A2A；第三，**PageAgent 实现方案的选择**——如何让 AI 自动操作前端界面。这三个决策我们都做了系统调研和横向比较，我来逐一说明我们的选择和背后的思考。"

---

## 二、多 Agent 编排框架选型

### 横向对比

| 框架 | 核心能力 | 优势 | 劣势 | 接入成本 |
|---|---|---|---|---|
| **LangGraph** | 状态图驱动循环、checkpointing、human-in-the-loop | 生产级有状态工作流主流选择（2026） | 引入图定义语法；框架接管状态管理；调试复杂；版本迭代快 | 高 |
| **AutoGen** | 多 Agent 对话协作、互相 critique | 适合协商/辩论类开放任务 | 对话轮次不可控；token 消耗不可预估；不适合低延迟生产 | 中 |
| **手写 PipelineContext** | 确定性线性 DAG，完全可控 | 100行代码清晰表达流程；零框架依赖；完全可审计 | 需自实现 checkpointing | 低 |

### 话术（约 1.5 分钟）

> "我们调研了主流的三个方向：LangGraph、AutoGen 和手写 Pipeline。
>
> **LangGraph** 的核心能力是三件事：状态图驱动的循环编排、跨节点 checkpointing 持久化、human-in-the-loop 中断恢复。它在 2026 年是企业级有状态工作流的主流选择。但接入成本是：需要学习图定义语法，状态管理由框架接管，在合规域里框架版本迭代带来真实的维护风险。
>
> **AutoGen** 的核心是多 Agent 对话协作，适合需要协商和辩论的开放性任务。代价是对话轮次不可控、token 消耗难以预估，不适合对延迟敏感的生产场景。
>
> 我们**最终选择手写 PipelineContext**，原因是：我们的工单处理流程是**确定性线性 DAG**——分类→抽取→校验→工具调用→回单生成，这5步的顺序是业务规则决定的，不需要 LLM 动态路由，LangGraph 的图编排在这里是 over-engineering。更关键的是，在金融合规场景里我们要求**状态转换必须完全可预测、可审计**。手写 Pipeline 虽然需要自己实现 checkpointing，但我们完全掌控状态机逻辑，100 行代码清晰表达整个流程。"

### 可能的追问

**Q：手写不就是重复造轮子？**
> "LangGraph 的价值在于动态图路由和循环，我们的管道是静态的，不需要这个能力。更关键的是金融系统对依赖稳定性有很高要求，引入一个快速迭代的框架作为核心依赖，版本升级的维护成本是实实在在的工程风险。当业务需要真正的动态协作（如跨条线协同阶段），我们会引入 LangGraph——但目前的线性管道，手写是最简单最可控的选择。"

## 三、Agent 间协作协议：轻量 A2A 设计

### 话术（约 1.5 分钟）

> "在 Agent 间协作协议上，我们调研了 **Google A2A（Agent2Agent）协议**。A2A 在 2025 年 4 月发布，到 2026 年已有 150+ 组织采用（Linux Foundation 认证），是目前最有行业共识的 Agent 互操作标准。它解决的核心问题是：**跨组织、跨框架的 Agent 如何互相发现能力、委派任务**——定义了 AgentCard 能力声明、标准化的任务委派接口、以及跨网络边界的通信规范。
>
> 我们做了一个**有意识的裁剪决策**：完整的 A2A 协议针对的是'独立系统、各自有 owner、跨组织边界'的场景。但我们的 5 个 Agent 运行在同一进程、共享内存，在这个阶段引入完整的 A2A 网络协议是 over-engineering——等于用分布式协议解决函数调用问题。
>
> 所以我们的选择是：**取 A2A 的契约化理念，不背 A2A 的协议层**。每个 Agent 有一份 AgentCard——声明它的能力、输入 schema、输出 schema。这保留了 A2A 最核心的价值——可发现性和契约化——同时避免了不必要的网络层开销。
>
> 这个设计的前瞻性在于：进入第三阶段 30+ 跨条线协同场景时，不同条线的 Agent 天然就是'不同 owner、不同部门'，那时把 AgentCard 升级到完整 A2A 协议是自然的演进路径，不需要重构现有架构。"

### 可能的追问

**Q：AgentCard 和接口文档有什么区别？**
> "接口文档是给人看的静态文档。AgentCard 是机器可读的——Orchestrator 在运行时通过它动态发现一个 Agent 能做什么、接受什么输入、返回什么输出。这是 A2A 协议的核心理念：Agent 的能力是自描述的，而不是靠硬编码的调用约定。它让每个 Agent 可以独立演进，只要不破坏 AgentCard 的契约。"

## 四、PageAgent 实现方案选型

### 三大技术范式对比

| 范式 | 代表实现 | 原理 | 延迟 | 覆盖范围 | 前提 |
|---|---|---|---|---|---|
| **视觉感知** | UI-TARS（字节）、Claude Computer Use、Skyvern | 截图 → VLM 标注编号框 → 选编号 | 2-5s/步 | 任意 UI | 无 |
| **DOM/可访问性树** | browser-use（7.7万★）、原版 page-agent | 序列化 DOM → LLM 按索引操作 | <500ms/步 | 标准 HTML | 无 |
| **语义化动作协议** | **我们的方案** | 后端声明业务意图 → 前端语义 ID 定位 | 毫秒级 | 受控 UI | 必须拥有目标 UI |

**关键数字**（InfoWorld 研究）：从视觉切换到 DOM 原生，延迟从 2-5s 降到 500ms 以下，token 成本降低约 **10 倍**。

**学术支撑**：arxiv 2602.17245《Web Agents Should Use Typed Actions Instead of Click-Based Browsing》（2026）直接批评 DOM 索引范式——"以点击为主的操作导致**行为脆性、执行成本高、可审计性差**"，提倡语义化动作协议，正是我们方案的学术依据。

### 话术（约 2 分钟）

> "PageAgent 的核心技术问题是**'如何让 Agent 定位并操作页面元素'**，学术界和工业界当前有三条根本不同的技术范式。
>
> **第一条是纯视觉感知**，代表是字节跳动的 UI-TARS 和 Claude Computer Use。Agent 完全依靠截图理解界面，用 VLM 生成带编号边界框的截图来定位元素。覆盖范围最广，任何 UI 包括图片、Canvas、老系统都能处理，但每步 2-5 秒延迟、极高视觉 token 消耗，2026 年研究指出 VLM 空间定位准确率仍是挑战。
>
> **第二条是 DOM/可访问性树 + 索引定位**，代表是 browser-use（GitHub 7.7 万星）和原版阿里 page-agent。序列化 DOM 后让 LLM 按索引操作，相比视觉方案延迟降到 500ms 以下、token 成本降 10 倍。但 2026 年的 arxiv 论文直接批评这条路：'以点击为主的操作导致行为脆性、执行成本高、可审计性差'——DOM 索引随任何元素增删就会错位，长任务极易在中途崩溃。
>
> **第三条是语义化动作协议**，正是该论文提倡的方向：当你拥有目标 UI 时，主动暴露稳定的语义标识符，让 Agent 操作业务概念而不是 DOM 结构。改布局不破坏任何映射，延迟毫秒级，可审计性最强。
>
> 我们的方案是**'场景感知的双范式混合'**：自家 Vue 表单走第三范式的语义化确定性通道；外部遗留系统走 fork 的 ReAct 引擎走第二范式。这不是技术偏好决定的，是'是否拥有目标 UI'这个客观条件决定的。
>
> fork 阿里 page-agent 源码而非 npm 安装，是因为我们需要把语义化动作协议作为第一等公民深度集成——黑盒 npm 包做不到这种定制。裁剪了 22 个无关文件，复用核心 ReAct 循环 661 行，新增适配约 200 行，MIT License 合规。"

### 可能的追问

**Q：前端改了布局要重新改映射吗？**
> "不需要。语义化协议绑定的是业务语义 ID 而不是 DOM 索引。改布局、改样式、增删元素都不影响映射，只有业务上真的决定重命名一个字段概念才需要更新——那是业务变更本身的代价，不是技术选型的缺陷。相比之下，DOM 索引方案每次 UI 改动都会破坏所有自动化脚本。"

**Q：二次开发有版权风险吗？**
> "阿里 page-agent 使用 MIT License，允许商业使用、修改和分发，只要保留原始版权声明。我们在代码头部保留了完整版权声明，完全合规。"

## 五、为什么用多 Agent 不用单 Agent

### 研究综述

**支持多 Agent 的研究：**

- **arxiv 2505.18286**：多 Agent 系统相比单 Agent **准确率提升 1.1-12%，部署成本降低最多 20%**，原因归结为角色专一化和上下文隔离
- **arxiv 2604.07911**：上下文隔离消除了跨 Agent 的推理干扰（cross-agent contamination），无需上下文压缩
- **arxiv 2505.16997**：异构 LLM 配置（不同 Agent 用不同模型）带来**高达 8.4% 的性能提升**
- **Anthropic 内部研究**：多 Agent 方案相比单 Agent baseline 提升 **90.2%**，核心原因是并行子 Agent 覆盖更大问题空间

**反对声音（主动承认）：**

- **arxiv 2606.13003《The Illusion of Multi-Agent Advantage》**：不是所有任务都受益于多 Agent，多 Agent 优势被夸大
- **Nature 2026**：存在"能力饱和阈值"——当单模型能力足够强时，增加 Agent 数量不再提升甚至降低性能
- **LangChain 官方文档**：一个有正确工具和 Prompt 的单 Agent 通常能达到类似效果

### 话术（约 1.5 分钟）

> "关于'为什么用多 Agent 不用单 Agent'，我先说一个诚实的判断：学术界存在争议——2026 年有论文专门研究'多 Agent 优势的幻觉'，指出并不是所有任务都受益于多 Agent 架构，当单模型能力足够时增加 Agent 数量甚至会降低性能。
>
> 但我们的场景有三个具体理由让多 Agent 是合理的。
>
> 第一是**上下文隔离**。我们的 5 个 Agent 职责之间没有知识交叉——ClassifierAgent 只需要场景模式识别的上下文，ResolutionAgent 只需要工具 Schema 和字段映射。如果用单 Agent，这五类知识全部挤进同一个上下文窗口——在分类推理时也要包含所有工具的参数结构，这是纯粹的噪声。研究表明上下文隔离能带来 1.1-12% 的准确率提升。
>
> 第二是**合规可审计性**。金融系统里，'这个字段是谁提取的''这个风险判定是哪步做出的'必须独立可追溯。单 Agent 的推理过程是一个黑盒；5 个 Agent 给了我们 5 个独立的审计节点，每个 Agent 的输入输出都有完整的 trace 记录。这是合规要求，不是技术偏好。
>
> 第三是**异构 LLM 优化**。我们的业务 Agent 用 DeepSeek 网关，PageAgent 用阿里/Qwen，各自针对领域特点优化。异构多 Agent 研究表明这能带来最高 8.4% 的性能提升。单 Agent 架构在物理上无法实现这种分层 LLM 配置。"

### 可能的追问

**Q：你的多 Agent 和单 Agent 加5个工具有什么本质区别？**
> "工具是无状态的函数调用，Agent 有自己的推理上下文和决策能力。更重要的是：5 个 Agent 意味着 5 个独立的审计节点——每个 Agent 的输入、输出、推理过程都被独立记录在 trace_steps 里。在金融合规场景下，这种可审计性是硬性要求，不是可选项。"

## 六、确定性优先 vs LLM 自主决策

### 话术（约 1.5 分钟）

> "在业务处理逻辑上，我们选择了**'确定性规则优先，LLM 只做兜底'**，而不是让 LLM 全程自主决策。
>
> 这是一个经过深思的选择。金融工单场景有两个硬约束：**字段不能幻觉**和**结果必须可审计**。纯 LLM 自主决策有两个具体问题：第一，幻觉风险——LLM 可能'发明'不存在的字段值；第二，成本问题——700+ 场景、330 万工单量，如果每张工单都要 LLM 做复杂推理，成本不可接受。
>
> 我们的方案是：**先跑确定性通道**，用正则、字段 schema、预设规则做快速抽取——当所有必需字段都能确定性提取时，整个发单侧只需要 1 次 LLM 调用、约 3 秒完成。只有在规则无法覆盖时才触发 LLM，而且 LLM 的职责被限定为'填补空缺'，不允许覆盖已经确定性提取的值。
>
> **关于 700+ 场景的扩展性**，配置不是一次性手工写 700 份，而是采用**'渐进式确定性化'**：新场景初期走 LLM 全自主提取（无需配置，灵活适应）；积累足够样本后 LLM 辅助生成配置草稿、运营人员校验通过后提升为确定性快速通道。场景越成熟，确定性比例越高，每单成本越低。这样 700 条配置是随业务积累自然生长的知识库，而不是一次性的人工任务。"

### 可能的追问

**Q：确定性规则感觉多 Agent 没什么意义？**
> "确定性是在已知场景的 happy path 上的优化，它和多 Agent 不矛盾。我们的多 Agent 价值体现在三个地方：上下文隔离提升准确率、独立审计节点满足合规、以及异构 LLM 配置的性能优化。在长尾未知场景和跨条线协同场景里，LLM 的自主决策能力才是核心——系统根据场景成熟度动态分配确定性和自主性，这是真正的创新点。"

---

## 七、收尾总结

> "总结一下我们的选型思路：**不追求技术新颖性，追求对业务约束的精准匹配**。LangGraph 强大但我们不需要动态图；A2A 成熟但我们不需要跨网络协议；纯 LLM 自主决策灵活但我们不能接受幻觉风险。每一个选择都对应一个具体的业务或工程约束，而不是为了技术而技术。这也是我们把 AgentCard 设计成面向 A2A 可升级的形态——不是当前阶段的需要，而是为第三阶段 30+ 跨条线协同场景预留了演进路径。"
