## 选择的方案

**方案 A：共享配置文件**

### 架构

```
semantic_targets.json (单一事实源)
       ↓
       ├── 后端: orchestrator/semantic_targets.py
       │   ├── load_semantic_targets() → 带 @lru_cache
       │   ├── get_scene_targets()
       │   └── API: GET /api/semantic-targets
       │
       └── 前端: sunpilot/semanticAdapter.ts
           ├── ADAPTERS (静态配置，与后端同步)
           └── getSemanticTargets() → 本地 fallback
```

### 优势
- ✅ 配置集中管理，修改一处即可
- ✅ 版本控制友好，易于审计
- ✅ 前后端强制同步，消除漂移
- ✅ 支持运行时验证和热加载
- ✅ 保留前端 fallback，无运行时依赖

## 消除的问题

### 问题 1: 重复定义 ✅ 已解决
**原状态**: 
- 后端: `main.py` 硬编码 12+ targets
- 后端: `orchestrator.py` 硬编码 5+ targets
- 前端: `semanticAdapter.ts` 维护 40+ targets（含重复）

**现状态**:
- 单一配置: `semantic_targets.json` (31 个 targets)
- 后端: 动态加载，0 处硬编码
- 前端: 静态配置与后端同步

### 问题 2: 语义漂移 ✅ 已解决
**原状态**: 
- `dispatch-*` 与 `draft-*` 两套并存
- 前端有 `draft-title`, 后端只用 `dispatch-title`
- 无法确定哪个是规范命名

**现状态**:
- 规范命名: `dispatch-*` 作为标准
- `draft-submit` 标记为 `dispatch-submit` 的 deprecated 别名
- 配置文件明确定义别名关系

### 问题 3: 维护成本 ✅ 已解决
**原状态**:
- 新增 target 需修改 3 处代码
- 前后端容易不同步
- 无自动验证机制

**现状态**:
- 新增 target 只需修改 1 个配置文件
- 自动验证脚本确保前后端一致
- API 端点支持运行时查询
