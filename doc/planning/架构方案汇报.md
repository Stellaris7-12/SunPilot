# TicketAgent 架构方案汇报

> 2026-07-23

---

## 一、问题

招商银行信用卡工单系统：330万件/年，700+业务场景，300+部室，近万员工。
单张工单从发单到回复约 30 小时，坐席需在 13 个业务系统间切换，手动复制粘贴。

核心挑战：**700+ 场景的工单结构千变万化——伪冒预防有投诉人信息组和案件编号，市场企划有卡片列表和订单号，征信有逾期状态和是否敏感标记。如何用同一套架构处理所有场景？**

---

## 二、核心架构

### 2.1 两层 AI 协作

```
业务大脑（后端多 Agent）              执行手（前端 PageAgent）
┌────────────────────────┐           ┌──────────────────────────┐
│ ClassifierAgent  分类   │           │  收到一份「执行清单」       │
│ IntakeAgent      提取   │  ──→     │  逐条找到页面元素          │
│ EscalationAgent  校验   │ pageHints │  填入/点击/滚动           │
│ ResolutionAgent  工具   │           │  鼠标动画 + 步骤展示       │
│ NotificationAgent 回单  │           └──────────────────────────┘
└────────────────────────┘
          ↑
   workflow_config.json
   （700+ 条配置，数据驱动）
```

后端 Agent 管 what（填什么、在哪填），PageAgent 管 how（怎么漂亮地执行出来）。
两个大脑之间通过一份「执行清单」通信，不直接耦合。

### 2.2 pageHints 是什么

一份结构化的执行清单。后端 Agent 完成分析后输出：

```json
[
  {"action":"input","target":"dispatch-customerId","value":"C88123","label":"填入客户号"},
  {"action":"input","target":"dispatch-customerName","value":"王小明","label":"填入客户姓名"},
  {"action":"select","target":"dispatch-scene","value":"优惠券补发","label":"选择业务场景"},
  {"action":"stop","target":"dispatch-submit","label":"等待坐席确认提交"}
]
```

PageAgent 执行这份清单不需要 LLM——它已经知道「填哪个元素、填什么值」。
每步 400ms，5 步 2 秒。不是每步调 LLM 观察 DOM 猜该填哪。

## 三、700+ 场景的泛化方案：配置驱动

### 3.1 核心原则

```
700+ 场景 ≠ 700 套代码
700+ 场景 = 1 套 Agent 逻辑 + 700 条 JSON 配置
```

差异不在代码，在数据。同一种「填表」动作，只是「填什么字段」「选项有哪些」不同。

### 3.2 workflow_config.json

每个场景一条配置，登记了：场景有哪些字段、每个字段在页面上对应哪个 HTML 元素、哪些必填、推荐哪个业务工具。

```json
{
  "scenarios": {
    "FRAUD_PREVENTION": {
      "label": "伪冒预防",
      "recommended_tool": "customer.lookup",
      "requires_human_confirmation": true,
      "fields": [
        {"name":"customerId","label":"客户号","target":"dispatch-customerId"},
        {"name":"customerName","label":"客户姓名","target":"dispatch-customerName"}
      ],
      "specificFields": [
        {"name":"callId","label":"CALLID","target":"dispatch-callId","type":"text","required":true},
        {"name":"callerNo","label":"主叫号","target":"dispatch-callerNo","type":"text"},
        {"name":"complainantName","label":"投诉人姓名","target":"dispatch-complainantName","type":"text","required":true},
        {"name":"caseNo","label":"案件编号","target":"dispatch-caseNo","type":"text"},
        {"name":"complaintContent","label":"被投诉内容","target":"dispatch-complaintContent","type":"textarea"}
      ]
    },
    "MARKET_PLANNING": {
      "label": "市场企划",
      "recommended_tool": "benefit.query",
      "fields": [
        {"name":"customerId","label":"客户号","target":"dispatch-customerId"},
        {"name":"customerName","label":"客户姓名","target":"dispatch-customerName"}
      ],
      "specificFields": [
        {"name":"cardList","label":"卡片列表","target":"dispatch-cardList","type":"text"},
        {"name":"cardName","label":"卡片名称","target":"dispatch-cardName","type":"text"},
        {"name":"remark","label":"订单号","target":"dispatch-remark","type":"text"},
        {"name":"customerFeedback","label":"客户反馈情况","target":"dispatch-customerFeedback","type":"textarea"}
      ]
    }
  }
}
```

### 3.3 三个环节的联动

```
workflow_config.json         发单表单 Vue 模板              发单Agent
┌──────────────────┐       ┌──────────────────────┐       ┌─────────────────┐
│ fields: [        │       │ <input               │       │ 从通话记录提取:   │
│  {name:"callId", │──①──│  data-page-agent-    │       │ callId=xxx       │
│   target:"draft- │       │  target="draft-callId"│──②──│ → 查配置 → 知道  │
│   callId"}       │       │ >                     │       │ callId 对应页面   │
│ ]                │       └──────────────────────┘       │ target=draft-callId│
└──────────────────┘                                       └─────────────────┘
                                                                    │
    ①: 配置定义了 "callId 字段在页面上的 DOM 元素叫 draft-callId"        │
    ②: 发单Agent 提取到 callId=xxx，查配置知道 target=draft-callId      │
    ③: 发单Agent 输出 pageHint: {target:"draft-callId", value:"xxx"}  ←┘
```

### 3.4 新增一个场景的流程

```
零行代码。只改配置和模板。

1. 在 workflow_config.json 加一条 "场景名": {fields, specificFields}
2. 在发单表单加对应的 <input data-page-agent-target="draft-xxx" />
3. 完成。发单Agent 下次识别到这个场景时，
   自动查配置 → 提取字段 → 输出 pageHints。
   Agent 逻辑和执行器零改动。
```

## 四、发单 Agent 和回单 Agent 如何与 PageAgent 协作

### 4.1 发单侧

```
通话记录文本
  → 发单Agent（1次LLM）: 分类 + 提取通用字段 + 查配置获取特有字段 + 提取特有字段
  → 输出 ticketDraft + pageHints（一份执行清单）
  → PageAgent 按清单逐条执行: 🖱填入客户号 → 🖱填入投诉人姓名 → 🖱选择场景 → ⏸等坐席提交
  → 坐席点提交 → 工单创建 → 自动跳转详情页
```

### 4.2 回单侧

```
坐席点"AI处理"按钮（不走 PageAgent）
  → 后端 5 Agent 管道执行:
    Classifier → Intake → Escalation → Resolution → Mock Tools → Notification
  → 完成 → AiProcessResult + PageTask（含 fillTextarea + locateEvidence）
  → SSE 推送到前端 Store
  → PageAgent 按 PageTask 执行: 🖱填入回单 → 🖱滚动到证据区 → ⏸等坐席结案
```

### 4.3 关键设计决策

- **PageAgent 不点"AI处理"按钮**。那是坐席的操作。PageAgent 只做填表、填回单、滚动定位等页面操作。
- **后端 Agent 输出结构化 PageTask，不是自然语言**。不再让 LLM 从一段文本中重新提取字段值——值已经是结构化的，直接给执行器。
- **PageAgent 为未知场景保留 ReAct 兜底**。快车道处理已知表单，ReAct 处理页面布局不确定或外部遗留系统。

## 五、调研过程与关键决策

### 5.1 PageAgent 方案选择

| 方案 | 评估 |
|------|------|
| 手写页面操作逻辑 | 每个场景一套代码，700 套无法维护。否决 |
| npm 安装阿里 page-agent | 快但定制受限，PolicyLayer 无法做硬约束。否决 |
| 裁剪阿里 page-agent 源码 | 保留 ReAct 引擎 + SimulatorMask 动画，自己做业务适配。采纳 |

裁剪后的 PageAgent 保留了 Ali page-agent 的核心能力（ReAct 循环、DOM 脱水、W3C 点击序列、SimulatorMask 鼠标动画），但 LLM 模型换成阿里云百炼 qwen3.7-plus，UI 面板改为 Vue 组件，DOM 索引定位改为语义属性定位，增加了确定性快车道执行器。MIT License 合规。

### 5.2 Agent 数量决策

最初设计了发单/回单/分发三个 Agent。实践中发现分发/跟踪 Agent 的大部分逻辑是确定性规则（缺字段检查、风险判断），拆为三个 Guard 模块（CompletenessGuard / RiskGuard / ToolResultGuard）放在 EscalationAgent 内部，不新增后端 Agent。最终保持 5 个业务 Agent。

### 5.3 编排框架考虑

调研了 LangGraph（基于图的 Agent 编排框架），结论是当前不需要。后端编排是 5 个节点的简单 DAG，LangGraph 的循环/并行/子图能力暂时用不上。改用手写 PipelineContext + 统一出口（_pause / _escalate / _finish_review / _fail），代码量小且可控。

### 5.4 Mock Tools 设计

真实系统需要对接 13 个外部业务系统。Demo 阶段用 Mock Tools 模拟——建了 7 张 mock_* 表（客户、卡片、交易、权益、申请、券、权限），每张表代表一个业务域。Agent 不知道数据来自 Mock 还是真实系统——`customer.lookup(客户号)` 对 Agent 是透明的。换成真实接口只需改 executor 层的实现。

## 六、最终业务解决方案介绍

### 6.1 一句话

"坐席挂断电话后，AI 自动理解通话内容、识别业务场景、从各系统调取数据、填好工单表单、调用业务工具处理、生成回复草稿——全过程坐席只需要点「确认提交」和「确认结案」两个按钮。"

### 6.2 改造前 vs 改造后

```
改造前（人工全流程）:
  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 听通话    │→│ 手动摘抄  │→│ 翻 13 个  │→│ 手动填表  │→│ 手动写   │
  │ 看记录    │  │ 客户信息   │  │ 系统查数据 │  │ 发单      │  │ 回单回复  │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
     30 秒         3 分钟          5 分钟         2 分钟         10 分钟
                                                          ≈ 20 分钟/张工单

改造后（AI 辅助）:
  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 选通话记录 │→│ AI 自动    │→│ 坐席确认   │
  │ 点"发单"   │  │ 分析+填表  │  │ 提交+结案  │
  │            │  │ +拉数据+回单│  │            │
  └──────────┘   └──────────┘   └──────────┘
      2 秒          10 秒           5 秒
                            ≈ 17 秒/张工单
```

### 6.3 发单场景详解

坐席刚挂断电话，系统右侧已有一条通话记录："客户王小明（C88123）来电，618 活动达标 50 元优惠券未到账，要求补发"。

坐席点击「根据这通电话帮我发单」。系统自动完成：

1. **发单Agent 读取通话记录**（1 次 LLM，~3 秒）
   - 识别场景：优惠券补发
   - 提取字段：客户号=C88123、姓名=王小明、券类型=50元优惠券、原因=618活动达标未到账
   - 查客户资料系统：补全手机号 138****6789、卡尾号 8812

2. **PageAgent 自动填单**（确定性执行，~3 秒）
   - 鼠标移动到「客户姓名」输入框 → 填入「王小明」
   - 鼠标移动到「客户号」输入框 → 填入「C88123」
   - 鼠标移动到「业务场景」下拉框 → 选择「优惠券补发」
   - ...逐字段填入，每一步在右侧 SunPilot 面板中可见

3. **坐席确认提交**（1 次点击）
   - 所有字段已填好，坐席只需点「一键提交」

### 6.4 回单场景详解

工单创建后跳转到详情页。坐席点击「AI处理」按钮。系统自动完成：

1. **5 个 Agent 依次处理**（4-5 次 LLM，~10 秒）
   - ClassifierAgent：确认场景为优惠券补发
   - IntakeAgent：再次提取结构化字段
   - EscalationAgent：检查字段完整性（✅完整）+ 风险判定（✅低风险）
   - ResolutionAgent：选择业务工具 `coupon.reissue`，构建参数
   - Mock Executor：模拟调用券系统 → 补发成功 → 生成证据编号 EVID-001
   - NotificationAgent：生成回单 "尊敬的王小明客户，您参加618活动达标的50元优惠券已补发..."

2. **SunPilot Panel 实时展示进度**
   - 🧠 ClassifierAgent: 识别为优惠券补发 (2.1s)
   - ✅ IntakeAgent: 提取 3/3 个字段 (1.8s)
   - 🛡 EscalationAgent: 低风险，通过 (1.5s)
   - 🔧 ResolutionAgent: 选择 coupon.reissue (1.2s)
   - 💬 NotificationAgent: 生成回单草稿 (2.3s)

3. **PageAgent 自动填入回单**（确定性执行，~2 秒）
   - 将 186 字回单草稿填入回单编辑器
   - 滚动到证据区域，高亮 EVID-001

4. **坐席复核结案**（1 次点击）
   - 复核回单内容 → 点「提交复核并结案」

### 6.5 不同业务类型的差异化处理

当坐席处理的不是优惠券补发，而是伪冒预防工单时：

1. 发单Agent 识别场景为「伪冒预防」
2. 表单自动切换——出现投诉人信息组（投诉人姓名、证件号、联系电话）、案件编号输入框、被投诉内容框。优惠券字段消失。
3. 发单Agent 从通话记录中提取这些特有字段，PageAgent 填入
4. 回单侧 EscalationAgent 判定伪冒场景为高风险 → 不会自动填回单 → 定位风险原因 → 停在人工确认区

同一个系统，同一套代码。不同的场景，不同的表单，不同的处理路径。

### 6.6 700+ 场景如何覆盖

系统的 700+ 场景泛化不靠写 700 套代码，而靠两份配置：

- **workflow_config.json**：每个场景登记了「有哪些字段、哪些必填、字段在页面上的 HTML 元素名叫什么、推荐用哪个业务工具」
- **发单表单模板**：每个字段加了 `data-page-agent-target` 属性，告诉 PageAgent「这列对应配置里的哪个字段名」

新增一个场景 = 在 JSON 里加一条配置 + 在表单模板里加几个 HTML 标签。Agent 逻辑一行不改。运营团队可以维护配置，开发零介入。

试点验证了 3 个场景（覆盖总工单量 70%）。扩展到 700+ 场景是配置工作。

### 6.7 安全边界

系统为不同场景预设了风险等级。高风险场景（伪冒、交易争议）的处理路径与低风险场景完全不同：AI 会自动填表和生成回单，但提交和结案按钮始终由坐席操作。在伪冒场景中，AI 不会自动结案——它定位风险原因后停在人工确认区，等待有权限的处理人员接管。Mock 工具模拟了真实业务系统中的权限校验——部分高风险操作（如修改客户地址）标记为「需人工确认」，即使参数齐全也不会自动执行。

## 七、当前进度与答辩准备

### 7.1 已完成

- 完整业务闭环：通话记录 → 发单Agent → 填单 → 工单创建 → 5 Agent 管道 → 工具调用 → 回单生成 → 复核
- 阿里 page-agent 源码裁剪集成（ReAct 引擎 + SimulatorMask + Vue Panel）
- Agent 间数据契约规范化（DTO + AgentCard schema）
- PageTask 协议 + 确定性快车道执行器
- 数据库治理与完整审计日志链路
- 9 个 smoke 脚本 + 前端协议检查自动通过

### 7.2 答辩前最后冲刺

- 工单表单差异化（不同业务类型展示不同字段结构）
- 发单/回单页面分离
- PageTask 快车道与后端打通

### 7.3 答辩主动说明的边界

- 当前 demo 覆盖 2-3 个场景。700+ 场景的泛化靠配置驱动——新增场景只是加 JSON 配置，不需要改代码。架构设计已验证，全量覆盖是运营配置工作。
- Mock Tools 是外部系统替身，不是真实银行系统直连。架构抽象层是正确的。
- 安全层（PolicyLayer、白名单拦截）是后续阶段，当前 demo 不做。
