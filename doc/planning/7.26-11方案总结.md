# SunPilot 信用卡工单智能处理引擎 —— 项目完整总结

## 一、项目背景与业务痛点

### 1.1 业务规模与现状
SunPilot 项目服务于某大型金融机构的信用卡工单处理体系，其业务规模极为庞大：

- **年工单处理量**：330 万件
- **业务场景覆盖**：700+ 种（涉及伪冒预防、伪冒调查、市场企划、客户经营、征信查询等）
- **组织参与广度**：百余个部室、近万名员工参与
- **工单模板与字段**：百余张模板，每张含 50 余个字段

### 1.2 核心业务处理流程
业务处理分为发单侧和回单侧两个方向：

**发单侧（坐席接听用户来电）**：
用户致电 → 系统拉起通话页面 → 坐席人工识别用户诉求 → 点击对应工单类别 → 在 10+ 业务系统间反复切换、手动复制粘贴信息 → 填写工单并投递。

**回单侧（坐席处理待办工单）**：
点击待处理工单 → 根据诉求人工跳转到其他系统 → 完成业务处理 → 填写工单处理反馈。

### 1.3 核心痛点
- **发单侧痛点**：坐席在 10+ 业务系统间频繁切换，大量手动复制粘贴，效率极低且易出错。
- **回单侧痛点**：回复严重依赖个人业务经验，回复质量参差不齐；70% 的回单内容虽来自系统接口，但仍有 30% 需人工补充。
- **时效痛点**：单张工单从发单到回复的平均时长达 **24 小时以上**。

## 二、项目目标

项目核心目标是 **“让 AI 自动完成重复劳动，坐席只做最终确认”**，分两阶段推进：

| 阶段 | 范围 | 核心目标 |
|------|------|----------|
| **试点阶段** | 5 个真实场景（Mock 数据驱动） | 处理时长压缩 50%，发单效率提升，80% 工单实现“一键发单” |
| **全量阶段** | 700+ 场景全覆盖 | 自动处理、自动回单，运营团队维护配置，头部场景实现可观的人力节省（**？** 人/年） |

## 三、核心技术方案（含您的关键更正）

### 3.1 顶层设计思想：双轨制自动化架构

这是整套方案最核心的设计逻辑，也是需要特别澄清的一点。整套系统根据目标系统的可接入性，**分两条轨道运行**：

- **轨道一（主航道，内部可接入系统）**：完全由**后端 5 个 Agent** 闭环完成，**不引入 PageAgent**，直接通过 API 调用操作内部系统，实现纯后端自动化发单与回单。
- **轨道二（兜底航道，外部遗留系统）**：当面对**无 API 接口、无法改造、不允许接入**的外部遗留系统时，才引入 **PageAgent**，以后端 5 Agent 输出的 `pageHints` 为指导，通过 **ReAct 自主探索模式**进行无侵入式的 UI 自动化操作。

> **设计精髓：API 优先，UI 兜底。用确定性接口覆盖 70%+ 的主场景，用 ReAct 探索解决“最后一公里”的历史系统对接难题。**

---

### 3.2 业务大脑：后端 5 Agent 管道（核心处理层）

无论走哪条轨道，**后端 5 Agent 都是不变的“业务大脑”**。它运行在服务端，无界面感知，专注于语义理解与业务逻辑推理。整个处理流程被拆解为**确定性流向的 5 个节点**，通过手写的轻量级 `PipelineContext` 串接（不采用复杂的 LangGraph 图编排），保证了链路的高效可控。

五个 Agent 的具体职责如下：

| Agent | 职责 | 输入 → 输出 |
|-------|------|------------|
| **ClassifierAgent**（分类） | 将用户的自然语言诉求映射到内部的工单模板 ID（700+ 场景之一），将开放问题收敛为封闭集合。 | 通话文本 → 场景标识（如“优惠券补发”） |
| **IntakeAgent**（提取） | 根据 Classifier 确定的场景，动态加载对应的 JSON Schema，只提取该场景下的特有结构化字段（如客户号、姓名、券类型等）。 | 场景标识 + 通话文本 → 结构化字段键值对 |
| **EscalationAgent**（校验与风控） | 聚合了 3 个 Guard 模块（完整性检查、风险判定、合规校验）。对提取的字段做质检，并判定风险等级（低/高风险）。 | 结构化字段 → 校验结果 + 风险等级 |
| **ResolutionAgent**（工具选择） | 根据场景选择对应的后端业务工具/微服务 API（如补券接口 `coupon.reissue`、调额接口、解冻接口等），并将提取的字段构建成该 API 所需的 JSON 参数。 | 场景标识 + 结构化字段 → 标准化的 API 调用参数 |
| **NotificationAgent**（回单生成） | 使用结构化模板（非纯大模型自由发挥），将提取的数据填入预设的回单话术模板中，生成标准化的回单草稿。 | 场景标识 + 结构化字段 → 回单草稿文本（如 186 字） |

**输出契约**：5 Agent 最终输出两份数据：
- `ticketDraft`：纯数据负载（结构化字段 + 回单正文）
- `pageHints`（仅轨道二需要）：抽象的 UI 操作清单（如“在客户号栏填入 C88123”），供 PageAgent 使用。

**性能数据**：
- 发单侧：**1 次 LLM 调用**，约 3 秒完成场景识别与字段提取。
- 回单侧：**4-5 次 LLM 调用**，约 10 秒完成全管道处理。

---

### 3.3 执行手脚：PageAgent（仅用于轨道二——外部遗留系统兜底）

PageAgent **不是默认执行器**，而是只在轨道二中启用。它运行在浏览器端，负责将后端 5 Agent 输出的 `pageHints` 翻译为实际的前端 DOM 操作。

针对外部系统未知的 DOM 结构，PageAgent 启动 **ReAct 自主探索模式**，形成闭环：

1. **观察（Observe）**：爬取当前页面的 DOM 树结构、按钮文本、输入框 label。
2. **推理（Reason）**：结合后端提供的 `pageHints`（如“需要在客户号栏填入 C88123”），推理出该操作在当前页面中可能的元素定位策略（如通过 label 文本匹配、模糊 XPath 搜索等）。
3. **行动（Act）**：尝试点击/输入。若失败，则根据页面反馈调整策略（如尝试相邻元素、属性模糊匹配等），直至完成所有填单步骤。

**性能数据**（轨道二场景）：
- 每步耗时 2-5 秒，全程需 5-10 次 LLM 调用（速度远慢于轨道一，但解决了无 API 系统的对接难题）。

---

### 3.4 双轨流程对比（实际落地路径）

| 流程环节 | 轨道一：内部可接入系统（API 直连） | 轨道二：外部遗留系统（UI 兜底） |
|----------|-----------------------------------|--------------------------------|
| **发单侧** | 语音流 → 5 Agent 提取/分类 → 直调 API 创建工单 → 坐席一键确认提交 | 语音流 → 5 Agent 提取/分类 → 生成 `pageHints` → PageAgent 以 ReAct 探索外部系统界面并逐字段填入 → 坐席确认提交 |
| **回单侧** | 工单触发 → 5 Agent 校验/调工具/生成回单 → 直写数据库/消息队列 → 坐席复核结案 | 工单触发 → 5 Agent 生成回单草稿 + `pageHints` → PageAgent 以 ReAct 探索外部系统编辑器并填入回单 → 坐席复核结案 |
| **PageAgent 是否参与** | **否**（纯后端闭环） | **是**（UI 自动化兜底） |
| **LLM 调用次数** | 发单 1 次 + 回单 4-5 次 | 发单 1 次 + 回单 4-5 次 + ReAct 额外 5-10 次 |
| **适用占比** | 约 70%（内部系统接口可覆盖） | 约 30%（外部遗留系统） |

## 四、关键技术调研与决策

项目在方案设计阶段做了三个关键的技术选型决策，核心原则始终是：**简单、可控、可维护**。

### 4.1 Agent 数量决策（为什么是 5 个？）
- 最初设想是 3 个 Agent，但在实践中发现分发逻辑实质上是**确定性规则**（先分类→再提取→再校验→再调工具→最后生成回单），因此拆解为 5 个职责单一的 Agent，并将校验逻辑拆为 3 个 Guard 模块放入 EscalationAgent。
- 不采用 LangGraph 等图编排框架，而是手写 `PipelineContext` + 统一出口，代码量小且可控。

### 4.2 PageAgent 实现方案决策
经过三条路线的对比调研，最终选择了 **fork 阿里 page-agent 源码 + 自建适配层**的方案：

| 路线 | 方案 | 问题 | 结论 |
|------|------|------|------|
| 路线一 | 自研 LLM Planner 生成执行计划 | LLM 看不到 DOM，存在“蒙眼决策”风险 | 放弃 |
| 路线二 | npm 安装阿里 page-agent | 每步调 LLM 太慢，定制受限 | 放弃 |
| **路线三（采纳）** | **fork 源码裁剪 + 自建 Vue 适配层** | — | **采用**，裁剪 22 个源文件，复用核心循环 661 行，新增适配代码约 200 行，MIT License 合规 |

### 4.3 编排框架决策
- 调研了 LangGraph，但发现工单处理的 5 个节点是简单的 DAG（有向无环图），不需要复杂的图编排和循环。
- 最终采用手写 `PipelineContext` 串接，统一出口，轻量且易于维护。

## 五、配置驱动的泛化能力（解决 700+ 场景扩展）

项目实现了 **“1 个引擎 × N 条配置 = 全场景覆盖”** 的架构：

- **运营级 JSON 配置**：每个业务场景对应一份 `workflow_config` JSON 文件，包含该场景的专属字段列表、校验规则（正则）、调用的 API 名称、回单话术模板、关联的页面元素定位信息。
- **代码零变更**：新增或调整场景时，只需运营团队维护 JSON 配置，**无需开发介入**。
- **引擎动态加载**：5 Agent 管道读取配置后动态构建处理逻辑，同一套代码适配所有场景。

## 八、创新点总结

1. **双脑解耦 + 双轨执行**：业务大脑（5 Agent）与执行手脚（PageAgent）通过 `pageHints` 协议通信，且 PageAgent 仅在外部系统兜底场景下启用，内部系统走纯 API 轨道，实现了灵活性与效率的最佳平衡。
2. **配置驱动泛化**：700+ 场景 = 引擎 × 1 + 配置 × N，新增场景只需加 JSON，无需开发介入。
3. **分级策略兜底**：已接入的内部系统走 API（确定性执行，0 次额外 LLM），未接入的外部系统走 ReAct UI 探索（5-10 次 LLM），用架构设计解决了规模化落地难题。
4. **开源项目二次开发**：基于阿里 page-agent 开源项目 fork 裁剪，保留核心 ReAct 引擎 + SimulatorMask，适配 Vue 生态，完全自主可控。

## 十、最终价值主张

SunPilot 通过 **“API 优先，UI 兜底”的双轨制架构**，将信用卡工单处理从“人工在 10+ 系统间反复横跳”彻底升级为“内部系统全自动 API 闭环 + 外部系统 ReAct 智能兜底”的混合自动化模式。最终实现：
